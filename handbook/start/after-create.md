# 만든 뒤 개발하기

> 한눈에: 프로젝트를 만들었으면 새 프로젝트 폴더에서 새 세션을 열어 개발해요. 그 세션에서만 전용 스킬과 에이전트가 켜져요. 평소 말로 요청하면 에이전트가 설계부터 확인까지 순서대로 진행해요.

## 새 세션 열기

> [!IMPORTANT]
> pro-kit 폴더의 세션(생성기 세션)에서 이어서 개발하지 않아요. 새 프로젝트의 스킬, 에이전트, dev-cycle 규칙은 그 프로젝트에서 연 세션에서만 불러와요.

<!-- b:open-in-project -->
```bash
cd ../my-app
.agents/skills/impeccable/scripts/impeccable hooks on   # 화면 디자인 검사 켜기. 처음 한 번만
claude                                                   # 신뢰 질문에 동의한다. Codex는 codex, Antigravity는 agy, Grok Build는 grok --trust
```
<!-- /b -->

도구마다 신뢰 질문이 켜는 것은 [지원하는 에이전트](supported-agents.md#신뢰-질문)에 있어요.

기존 프로젝트에 프로킷을 들였다면 새 세션이 `docs/first-request.md`의 요청대로 정밀 분석부터 이어 가요([기존 프로젝트에 도입하기](adopt.md)). <!-- edition:pro -->

## 처음 열면 보이는 질문

새 세션을 처음 열면 폴더를 믿을지 묻고, 옵션 없이 열었다면 명령마다 허락을 물어요. **모두 정상이에요.** 무엇을 어떻게 답하는지는 [처음 한 시간](first-hour.md#2-에이전트를-열고-처음-나오는-질문에-답하기)에 있어요.

## 이렇게 요청해요

> [!TIP]
> 처음에는 어떤 서비스인지부터 알려 주세요.

요청은 크기별로 모았어요. 크기에 맞게 요청하는 법과 문장 만드는 법은 [요청하고 이어 가는 법](ask-well.md)에 있어요.

| 크기 | 할 일 | 예시 프롬프트 |
|---|---|---|
| 처음 한 번 | 서비스 소개 | 필라테스 수업 예약 앱이야. 강사가 수업을 열고 회원이 예약해. 회원은 자기 예약만 봐. 이 내용으로 GLOSSARY.md와 docs/domain/project.md를 채워줘 |
| 처음 한 번 | 배포 준비 | Vercel 배포 준비해줘 | <!-- edition:ui | 처음 한 번 | 인터넷에 올리기 | GitHub Pages에 배포해줘 | --> <!-- edition:pro -->

스킬 이름을 몰라도 돼요. 요청에 맞는 스킬을 에이전트가 스스로 불러요([prokit 스킬](../skills/prokit-skills.md)).

멈추는 법(`Esc`), 사용량 한도에 걸렸을 때, 새 세션에서 이어 가는 법은 [요청하고 이어 가는 법](ask-well.md#이어-가는-법)에 있어요.

## 자세히

요청 하나는 이렇게 흘러요.

**요청** → **스펙과 화면 설계 확인** → **구현과 검사** → **내 확인** → **커밋과 배포**

- **만들기 전에 확인받아요**: 에이전트는 만들기 전에 스펙과 화면 설계를 보여 주고 확인을 받아요. 첫 화면은 디자인 카탈로그가 추천하는 스타일 1\~3위 중에서 골라요<!-- edition:pro -->. 기존 프로젝트를 들였다면 그 전에 지금 디자인을 유지할지 리디자인할지 먼저 한 번 물어요<!-- /edition -->([UI/UX 흐름](../design/ui-flow.md)).
- **큰 일은 진행 계획으로 나눠요**: 한 라운드로 끝나지 않는 큰 일은 Task로 나눈 진행 계획을 세우고 Task 하나씩 끝내요. 앞 Task가 끝나야 다음 Task를 열 수 있어요([정밀 분석과 진행 계획](../concepts/project-plan.md)). <!-- edition:pro -->
- **끝나면 직접 확인해요**: 기능이 끝나면 직접 써 보고 확인해 달라고 해요. <!-- edition:pro -->확인하면 운영 배포까지 할지 물어요(기본은 릴리스 후 배포, 원하면 건너뛰어요). <!-- /edition -->그다음 커밋과 push를 해요<!-- edition:pro -->. 배포 준비가 안 됐으면 묻지 않고 커밋과 push까지만 해요<!-- /edition -->([사용자 확인](../concepts/audit-and-confirm.md)).
- **하네스만 들였거나 배포 방법이 프로킷과 맞지 않으면 커밋까지만 해요**: 하네스만 들인 프로젝트(`adopt`)와 배포 방법을 아직 프로킷에 맞추지 않은 운영 중 프로젝트는 배포를 묻지 않아요. 이때 push는 요청할 때만 하고, 운영 중인 프로젝트는 배포 방법을 프로킷에 맞춘 뒤에야 위 순서를 따라요. <!-- edition:pro -->
- **스킬 업데이트는 하루 한 번 확인해요**: 작업을 시작할 때 하루 한 번 외부 스킬에 새 버전이 있는지 확인해요. 있으면 업데이트할지 물어요(지금, 항상 자동, 나중에, 다시 묻지 않기)([설치와 업데이트 구조](../skills/install-and-update.md)).
- **전문 작업은 공식 스킬과 수행자가 맡아요**: 공식 스킬과 전문 수행자가 구현·검토를 맡고, 프로킷은 범위·증거·재지시와 최종 `prokit-reviewer` 게이트를 관리해요. ponytail을 고르고 Codex 네이티브 플러그인을 선택 설치했더라도 `$ponytail:ponytail-review`와 프로젝트 스킬 대체 경로를 같은 검토에 함께 쓰지 않아요([공식 스킬과 연결](../skills/official-skills.md)).
- **첫 배포는 운영이에요**: Vercel 계정, 원격 DB, GitHub 저장소가 필요하고 에이전트가 준비 순서를 안내해요. 운영에 배포할 때마다 버전과 릴리스 노트를 보여 주고 동의를 받아요([Vercel 배포와 되돌리기](../deploy/vercel.md)). <!-- edition:pro -->
- **화면 디자인 검사는 명령으로 켜요**: `impeccable hooks on`은 스킬을 불러서 켜지 않아요. 개인(전역) impeccable 스킬이 있으면 훅 경로가 깨지기 때문이에요.
- **개발 명령에 자원 보호가 붙어요**: 새 프로젝트의 개발·빌드 명령은 용량과 여유 공간을 확인해요. 이미 프로킷을 설치한 프로젝트는 [템플릿 갱신 절차](../../AGENTS.md#기존-프로젝트에-템플릿-갱신-반영)로 H 라운드([케이스와 대조표](../concepts/cases.md))에서 반영해야 해요. 큰 환경은 함부로 지우지 않아요([위임과 자원 관리](../concepts/delegation-and-resources.md)).
- **프로젝트 소개를 채워 두세요**: `GLOSSARY.md`(용어집)와 `docs/domain/project.md`(프로젝트 소개)는 에이전트가 작업마다 읽어요. 채워 두면 새 세션에서 프로젝트를 다시 설명하지 않아도 돼요.
