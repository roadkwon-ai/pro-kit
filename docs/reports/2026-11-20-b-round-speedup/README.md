# 화면(B) 라운드 병목 개선

> 한눈에: 같은 화면을 세 번 찍던 확인을 묶음 한 번으로 바꾸고, 수행자를 이어 쓰고, 서로 기다릴 필요 없는 행을 함께 시작한다. 하네스 보증(독립 리뷰, critique A·B 격리, `[confirm]`, 실행하지 않은 검사를 통과로 적지 않기, 증거 형식, 위임 범위 대조)은 그대로 두었다.

측정일 2026-11-20(KST). 대상은 이 저장소 두 템플릿(`prokit-next-neon`, `prokit-next-supabase`)의 하네스다. 확인용 프로젝트는 Better-T-Stack 최신판(neon 생성 명령 그대로, `--brain none --simplicity ponytail --ui-skill impeccable`)이다.

### SendMessage 이어 쓰기와 audit

확인용 프로젝트에서 `claude -p`(Sonnet)가 `prokit-runtime-checker`를 띄워 `next-dev-loop`를 읽게 하고, 같은 에이전트에 SendMessage로 `agent-browser`를 읽게 했다. 훅 기록의 두 줄 모두 같은 `agent`(agent id)와 `agentType`이었다. audit은 같은 agent id가 그 뒤에도 일했으면 앞선 읽기를 센다(`lastWork`). 그래서 이어 쓴 수행자는 스킬을 다시 읽지 않아도 된다. 테스트 `dev-cycle-parallel.test.mjs`가 이를 고정한다(이어 쓰고도 그 뒤 일하지 않으면 받지 않는 경우 포함).

## B 라운드 시간 추정

같은 크기의 라운드를 바꾼 규칙으로 돌린다고 보고 단계마다 근거를 둔 계수로 추정했다. 보수·낙관 두 값이다. 실제 B 라운드 전체를 다시 돌려 잰 값은 아니다.

| 단계 | 기준선 | 바뀐 뒤(보수\~낙관) | 근거 |
|---|---|---|---|
| 구현 1단계 | 13.1분 | 7.1\~8.5분 | 섹션 4개를 두 위임으로 나눔(임계 경로 0.5\~0.6배), 바닥선 읽기 +8% |
| 구현 2단계 | 6.2분 | 1.8\~3.0분 | 같은 수행자를 이어 씀(-25\~-45%), 나눔 |
| 런타임 확인 | 12.7분 | 2.3\~3.8분 | 묶음 촬영 실측 0.3분 + 서버 확인·스크린샷 보기·보고 |
| critique A / B | 5.6 / 0.7분 | 2.2\~3.1 / 0.7분 | A가 묶음 스크린샷으로 화면을 봄. B(detector)는 그대로 |
| web-design-guidelines | 5.1분 | 5.1분(임계 경로 밖) | 런타임 확인과 함께 시작 |
| audit | 10.4분 | 4.2\~6.2분 | 대비·터치·넘침·Tab·테마를 묶음 측정으로 |
| 마감 | 8.9분 | 2.4\~4.3분 | 바닥선이 반복 지적 9건을 미리 막음(-35\~-50%), 이어 씀 |
| 벽시계(임계 경로) | 62.7분 | 20.6\~27.2분 | 57\~67% 단축 |
| 에이전트 시간 합 | 62.7분 | 34.8\~46.3분 | 26\~45% 단축. 나눈 구현은 에이전트 시간을 더 쓴다 |

계산식은 단계별 계수의 곱이고, 임계 경로는 `구현 → max(런타임, web-design-guidelines) → max(critique A, B, audit) → 마감`이다.

## 독립 코드 리뷰와 반영

러너 diff를 결론 없이 독립 리뷰어(Opus, 읽기 전용)에게 맡겼다. 결함 여섯 개를 찾았고 둘은 재현 테스트까지 썼다. 모두 고치고 회귀 테스트를 더했다(`tests/dev-cycle-parallel.test.mjs`). 리뷰어의 재현 테스트 두 개는 고친 판에서 결함이 닫힌 쪽으로 바뀌었다.

| # | 결함 | 고친 것 |
|---|---|---|
| 1 | 행을 `미실행`으로 먼저 채운 뒤 화면을 고치고, 고치기 전 묶음을 적어 다시 채우면 통과했다 | 그 행을 마지막으로 채운 때를 기준으로 본다 |
| 2 | 손으로 쓴 `packet.json`이 hash만 맞으면 통과했다(실행하지 않은 측정을 통과로 적는 길) | 판·측정 파일 항목·파일마다 hash를 `check`와 같은 함수로 보고, 편집 도구로 묶음 폴더를 고친 기록이 있으면 받지 않는다 |
| 3 | 인용 경로에 `..`이 들어가면 다른 작업 트리의 묶음을 읽을 수 있었다 | `.`·`..` 조각과 경로 중간에서 시작하는 인용을 받지 않고, 실제 경로가 `tasks/evidence/` 안인지 본다 |
| 4 | 재확인을 코드 리뷰보다 먼저 채우면 함께 시작한 리뷰어의 일을 세지 않았다("어느 순서로 채워도 된다"가 거짓) | 같은 병렬 묶음의 행은 서로 앞 행으로 보지 않는다. 코드 리뷰의 기준은 마감 행이다 |
| 5 | 기준이 봉인 시각이라, 찍은 뒤·봉인 전에 고친 화면을 놓쳤다 | 찍기 시작한 시각(`capturedAt`)을 기준으로 하고, 찍는 동안 지문이 바뀌면 봉인하지 않는다 |
| 6 | 기본 브라우저 세션 이름이 하나라 동시에 찍는 두 실행이 서로를 닫았다 | 기본 세션 이름에 프로세스 번호를 붙인다 |
| 덤 | 다크로 찍었는데 라이트로 그려진 뷰포트를 잰 것으로 쳤다 | `coverage.mismatch`로 따로 두고 빠진 뷰포트에 넣는다 |
| 덤 | 기록 캐시 키가 크기·수정 시각뿐이었다 | inode를 더했다 |

## eval (skill-creator 방식)

`evals/prokit-dev-cycle/evals.json`에 시나리오 45\~47을 더했다(저장소 규약대로 시나리오마다 기대 항목 5개). 같은 확인용 프로젝트를 둘로 나눠 기준선 하네스와 새 하네스를 넣고, `claude -p`(Sonnet 5.5, 쓰기 도구 막음)로 각각 돌렸다. 시나리오 45는 1차 결과를 보고 문서를 보강한 뒤 두 번 더 돌렸다. 여덟 답을 어느 판인지 모르는 독립 채점자(Opus)가 같은 기준으로 채점했다. 여러 부분으로 된 기대 항목은 모든 부분을 약속해야 PASS다.

| 시나리오 | 기준선 | 새 판 1차 | 새 판 보강 뒤 |
|---|---|---|---|
| 45 B 라운드 편성(나누기·바닥선, 묶음 촬영, 묶음 우선, 병렬, 이어 쓰기·보증) | 0/5 | 3/5 | 4/5, 3/5 |
| 46 이어 쓰기와 독립성(구현자에게 리뷰 금지, 낡은 묶음 거부, 보증 유지) | 2/5 | 4/5 | 같은 문서 |
| 47 모델·노력도 기본값과 사용자 설정 우선 | 1/5 | 5/5 | 같은 문서 |
| 합계 | 3/15(20%) | 12/15(80%) | 평균 12.5/15(83%) |

- 보증 위반(독립 리뷰, A·B 격리, `[confirm]`, 미실행을 통과로 적기)은 여덟 답 모두 0건이다. 기준선 46은 마감이 건드리지 않은 화면에 마감 전 스크린샷을 다시 쓰자고 했다. 보증 네 가지는 아니지만 낡은 묶음 규칙과 어긋난다.
- 새 판의 공통 감점: 묶음의 `sha256=`을 평가 지시에는 넣었지만 증거 칸에도 적는다는 말이 없었다(B 행 문구에는 있다. 실제 라운드에서는 audit이 경로만 적은 증거를 거부한다). 46 새 판은 A·B 격리를 다시 적지 않았다.
- 1차에서 새 판이 놓친 재확인 평가자 이어 쓰기와 보증 재확인은 병렬 표 칸과 "함께 시작해도 보증은 그대로다" 항목으로 보강했고, 보강판 한 번(45)에서 그 항목을 통과했다.
- `prokit-reviewer(ui)`의 web-design-guidelines 코드 검사는 브라우저를 쓰지 않아 묶음을 기다릴 이유가 없다. 처음 요청은 이 리뷰어도 묶음을 먼저 읽게 했지만, 런타임 확인과 함께 시작하게 바꿨다(묶음이 있으면 근거로 쓴다). 기대 항목도 이 규칙에 맞췄다.
- 한계: 시나리오마다 1\~3회라 편차를 말하기에는 적다(45 보강판 두 번이 4/5, 3/5). 실제 B 라운드 전체(구현부터 `[confirm]`까지)를 새 판으로 돌린 행동 eval은 하지 않았다.
- 비용: 8회 실행 합 약 $4.0(회당 $0.39\~0.61), 회당 43\~110초.

- 실측: `supervise`는 기록 3만 줄(활동 줄 포함)에서 83\~87ms다(세 번, 다른 작업 없이). 처음 잰 1.1\~1.4초는 테스트·eval과 동시에 돌던 때의 값이다. 테스트가 다시 읽기, 배정 밖 편집, 묶음 밖 촬영, 예산 초과, 같은 명령 반복 신호와 신호 없는 에이전트의 침묵을 고정한다.
- 활동 기록(보강): Claude Code는 이미 모든 Read에 기록 훅을, 모든 Bash에 셸 막기 훅을 건다. 두 훅이 하위 에이전트의 일반 파일 읽기와 허락한 셸 명령을 활동 줄로 남긴다. 새 훅 프로세스와 설치기 변경은 없다. 셸 명령은 비밀값이 섞일 수 있어 내용 대신 해시와 앞 낱말(`pnpm test`)만 남긴다. 같은 명령을 세 번 돌리면 `repeat` 신호가 "같은 오류로 실패한 것이면 멈추고 보고하라"를 낸다. audit은 활동 줄을 일한 기록으로 세지 않는다(테스트가 고정).
- 한계: 검색 도구(Grep·Glob)는 훅이 없어 보이지 않는다. 셸 막기 훅은 명령 전에 돌아 종료 코드를 모르므로, 고친 뒤 테스트를 다시 돌리는 정상 반복에도 신호가 난다(받은 에이전트는 이미 따르는 규칙을 다시 듣는다). Antigravity는 셸 훅이 없어 읽기만 보인다.
- eval 48(감독, 기대 항목 5개, 두 판에서 두 번씩, 블라인드 채점): 기준선 0/5, 0/5. 새 판 5/5, 5/5. 보증 위반은 네 답 모두 0건이다. 기준선 두 답은 "구현 시간 제한이 없다"며 개입하지 않았고, 한 답은 표준 뷰포트·테마를 근거 없이 줄였다. 새 판 두 답은 Main이 직접 쓴 문장에서 막힌 것을 묻지 않았다(그때는 기대 항목 밖으로 봤다).
- eval 48 다시 돌림(활동 기록 보강 뒤, 같은 방식): 1차 새 판은 5/5, 4/5였다. 4/5 답은 Main이 보내는 문장에서 막힌 것을 빠뜨렸다. `delegation.md` 9의 예산 초과 조치에 "보내는 문장에 한 일, 남은 일, 막힌 것을 모두 적는다"를 넣은 판은 5/5, 5/5다(기준선 두 답과 섞어 블라인드 채점, 기준선 0/5·0/5). 네 새 판 답 모두 같은 명령 반복을 감독 신호로 들었고, 보증 위반은 0건이다.
