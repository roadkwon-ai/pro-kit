# 프리셋 재사용과 dev-cycle 설계 검토

2026-10-09에 현재 작업 트리와 인접 `pro-kit-web`, `pro-kit-samples`를 읽고 검토했다. 기존 수정은 보존하고 두 템플릿의 판단 기준과 리뷰 연결을 보완했다. 인접 앱과 배포 대상은 변경하지 않았다.

## 결론과 작업 범위

프리셋은 공통 등록·팩·검증 절차 위에 독립 앱을 만드는 구조다. 매번 모든 것을 새로 만들지는 않는다. 개선 우선순위는 등록 목록의 중복과 누락을 줄이는 것이다. 디자인과 사용자 흐름이 다른 앱을 하나의 범용 화면 엔진으로 합치는 것은 권하지 않는다.

Ponytail, Superpowers, Vercel 구성 스킬과 Turborepo는 필요한 원칙을 이미 제공한다. 부족한 것은 그 원칙을 구현 전 결정·독립 리뷰·증거와 연결하는 프로킷 기준이었다. 새 스킬이나 의존성을 추가하지 않고 기존 하네스의 감사·보완 모드로 해결했다. 절차 정본은 기존 `docs/dev-workflow.md`이고, 새 DAG 명세나 설정 파서는 만들지 않았다.

## 등록 공통화의 구현 설계안

인접 저장소의 실제 구현은 이번 작업에 포함하지 않았다. 다음 순서의 작은 변경을 권한다.

1. 웹 카탈로그는 기존 `samples.json`, 배포된 팩 메타데이터는 `tutorials/packs.json`을 정본으로 유지한다. 화면 목록과 팩 목록은 역할이 달라 무조건 같은 목록으로 합치지 않는다. 촬영·공개·프리미엄·팩 제공 대상의 차이는 실제 조건으로 설명한다.
2. 현재 검사기에 신규 slug의 필수 메타데이터·페이지·자산·팩 링크 누락과 중복을 확인하는 검사를 더한다. 촬영 대상과 팩 제공 대상의 의도된 차이도 검사한다. 새 레지스트리 서비스는 만들지 않는다.
3. 같은 변경으로 늘 함께 고치는 카드 경로·배지·촬영 목록은 기존 카탈로그에서 파생하거나 해당 항목으로 옮긴다. 특수 query·초기 모달 닫기·예외 이미지 이름은 대상별 예외로 남긴다.
4. 팩의 화면 코드 전체를 공유 패키지로 옮기지 않는다. 실제 계약과 변경 이유가 같은 반복이 확인된 범위에서만 추출한다. export·팩 처리·검사는 이미 있는 도구를 사용한다.

확인은 신규 slug fixture, 필수 필드·자산 누락 fixture, 의도된 촬영 제외 fixture와 기존 프리셋의 링크·상호작용 회귀로 한다. 메타데이터 변경 전후 카탈로그 상세 페이지·촬영 경로·팩 링크가 같아야 한다. 배포와 릴리스는 별도 작업이다.

## dev-cycle에서 발견한 빈틈과 보완

|---|---|

| 환경 변수의 공개성·검증·캐시 책임이 여러 곳에 흩어짐 | 소비 앱, 로더·검증, 스키마, 공급 환경, 결과 변수와 캐시 입력의 결정 연결 |
| F의 공통화 범위가 같은 디렉터리에 한정됨 | 계획에서 확인한 공통 모듈의 실제 소비자도 검토 범위에 포함 |

판단 기준의 정본은 [재사용과 설정 설계](../../../templates/prokit-next-neon/files/.agents/skills/prokit-dev-cycle/references/reuse-design.md)다. UI·웹 스킬과 구현·리뷰 에이전트가 이 결정 위치를 전달한다. Supabase의 별도 RLS·Data API·비밀 키 규칙은 유지했다.

원저자 문서를 2026-10-09에 확인했다. 확인한 원본 SHA를 템플릿의 설치 버전으로 고정하지 않는다.

- [Ponytail 리뷰](https://github.com/DietrichGebert/ponytail/blob/9cc65d03aa2da1db7121b912d03596409ee340b8/skills/ponytail-review/SKILL.md)는 호출자와 실제 소비자를 읽고 정확성·안전·부하·테스트·성능·간결성을 검토한다. 계획 전용 모드는 없다.
- [Vercel 구성 스킬](https://github.com/vercel-labs/agent-skills/blob/063bee94c3f4df8453406c830b0a7df0f2860278/skills/composition-patterns/SKILL.md)은 React 재사용 API와 합성 경계를 다룬다. 모든 부품에 Provider를 추가할 근거는 아니다.

- [Turborepo 환경 변수 문서](https://turborepo.dev/docs/crafting-your-repository/using-environment-variables)는 소비 앱과 태스크의 캐시 입력, `.env` 로딩 책임, `passThroughEnv`와 결과 변수의 차이를 다룬다. 일반 설정 전체의 중앙화를 요구하는 지침은 아니다.

## 검증과 행동 평가

평가 전에 여섯 요청과 각 요청의 확인 항목을 고정했다. 합격 기준은 행동 확인 항목의 90% 이상, 비밀값 공개·범위 밖 수정·필수 검증 삭제가 없는 것이다. [평가 정의](../../../templates/prokit-next-neon/evals/prokit-dev-cycle/evals.json)에 실제 입력 파일과 확인 항목을 보관했다.

수정 전·후의 스킬 스냅샷, 같은 fixture·요청·쓰기 제한을 각각 독립 에이전트에게 주었다. 실행자는 채점표와 기대 답을 읽지 않았다. 설계·읽기 전용 요청을 수행하며 결과 파일만 쓸 수 있었다. 외부 설치·서비스·운영 비밀값은 사용하지 않았다. 결과는 별도 평가자가 채점했다.

평가 대상은 기존 UI 재사용, 다른 디자인의 독립 프리셋, 환경 변수·캐시, 소비자 한 곳의 추상화, 공식 스킬 부재, 잘못된 계획의 독립 거부다. 구현된 앱의 품질이나 브라우저 동작 평가와는 구별한다.

### 독립 설계 평가 결과

Codex 네이티브 실행자가 세션 설정을 상속해 설계를 작성하고, 실행자와 분리된 verifier가 익명 결과를 채점했다. 요청별 확인 항목은 동일 가중치다. 점수에 맞춰 기준을 바꾸거나 실패 결과를 삭제하지 않았다.

| 사례 | 기존 스킬 | 보완 1차 | 보완 2차 |
|---|---|---|---|
| 기존 UI 재사용 | 3/5 | 4/5 | 5/5 |
| 독립 프리셋의 경계 | 5/5 | 5/5 | 4/5 |
| 환경 변수와 캐시 | 1/5 | 3/5 | 4/5 |
| 소비자 한 곳의 추상화 | 4/5 | 4/5 | 5/5 |
| 미설치 스킬의 대체 | 5/5 | 5/5 | 4/5 |
| 잘못된 계획 거부 | 5/5 | 5/5 | 5/5 |
| 합계 | 23/30 (76.7%) | 26/30 (86.7%) | 27/30 (90%) |
| 치명적 실패 | 없음 | 없음 | 없음 |
| 사전 합격 기준 | 미달 | 미달 | 통과 |

1차의 미달은 환경 변수·설정 영향 기록 누락과 숨김 `.env.schema` 확인·기본값·공급 위치 누락에서 발생했다. 기존 스키마를 직접 열고 결정 필드를 기록하도록 보완했다.

2차에서 남은 실패는 기존 프리셋 디자인의 회귀 검사, 잘못된 환경 변수 값의 거부 확인, 미설치 스킬을 사용했다는 상충 기록이었다. 변경된 등록 데이터·도구의 기존 소비자 검사, 누락과 잘못된 값의 별도 검증 사례, 현재 요청의 설치 상태와 사용 기록을 대조하도록 좁게 보완했다. 같은 확인 항목으로 해당 사례와 잘못된 계획 거부를 집중 재평가했다. 결과는 18/20(90%)이고 치명적 실패는 없었다. 입력 파일은 21개 모두 일치했다. 미설치 스킬의 사용 기록, 기존 디자인 회귀와 잘못된 값 검증은 통과했지만 환경 변수 스키마·기본값·공급 위치 누락이 다시 나타났다.

이 편차를 보고 진입 스킬과 계획 리뷰어의 진입 절차에도 환경 변수 정본을 직접 읽고 기존 선언·기본값·공급 위치를 대조하는 필수 항목을 올렸다. 보완 후에는 이 불완전한 실제 평가 결과를 별도 리뷰어에게 넘겼다. 리뷰어는 환경 변수 정본을 직접 확인하고 `changes-required`, `max=medium`을 반환했다. `KRW` 기본값·선택 여부와 환경별 공급 계획 누락, 실제 소비자 없는 가격 공통화를 지적했다. 입력 파일은 변경되지 않았다. 이 결과는 승인 형식을 요구하는 audit을 통과할 수 없으므로 구현 전에 보완해야 한다. 이 마지막 게이트 검사는 설계 작성 점수와 구별한다.

보완 2차의 전체 점수는 합격선과 같다. 한 실행자가 여러 요청을 순서대로 처리한 축소 실험이며, 모든 모델의 안정성이나 실제 프로젝트 탐색 성능을 측정한 결과가 아니다. 집중 재평가의 점수는 전체 점수와 따로 적고 합산하지 않는다.

동작 회귀는 필수 설계 행의 순서·중복·누락, 결정 필드의 누락·빈 값·일반 검사 대체, 계획 리뷰의 N/A·PASS·미승인·high 결과 거부, 도구 실패의 partial close, 구판 F의 증거 메모 보존과 재업그레이드의 멱등성을 확인했다.

독립 코드 리뷰의 중요 지적은 반영 후 재리뷰에서 해소됐다. 남았던 문서 역할 설명과 fixture 격리도 고쳤다. 평가 입력은 사례별 JSON으로 나누고 기존 `evals.json`의 `files`에 연결했다. 실험의 입력 파일은 원본 문자열에 LF 하나를 붙여 생성했고, 동일한 바이트를 모든 실행에 사용했다. 실제 입력 파일에 추가·누락·의미 변경이 없음을 확인했다.

## 적용과 한계

두 템플릿에는 함께 반영했다. 이미 설치된 프로젝트는 그 프로젝트의 세션에서 템플릿 변경 반영 절차와 케이스 H를 따른다. 열린 라운드는 `table <케이스> --write --upgrade`로 새 행을 더할 수 있고 기존 증거를 보존한다.

audit은 필수 행과 결정 항목, 계획 리뷰의 승인 형식을 검사한다. 잘못된 설계나 거짓 스킬 사용 기록을 의미적으로 판정하는 검증기는 아니다. 이 부분은 실제 파일을 보는 독립 리뷰와 행동 평가가 맡는다. 이번 점수는 제한된 fixture의 설계 결과를 평가한 값이며 실제 프로젝트 전체 품질, 모든 모델·반복 실행의 안정성, 비용 절감률로 일반화하지 않는다.

신규 스킬·공통 UI 엔진·설정 파서·의존성·원격 변경·배포는 추가하지 않았다. 인접 저장소의 카탈로그 공통화는 설계안만 남겼고 실제 반영·재배포·실서비스 검증은 수행하지 않았다.
