BTS 스킬 연결 점검

요약

무엇을 어떻게 쟀나

  • BTS 3.44.1로 새 프로젝트를 만들고 bts-next-neon 템플릿(v0.6.1)을 설치한 fixture에서, 사용자가 새 세션에 칠 법한 요청 7개를 claude -p(Opus 5.5, 이 기기의 전역 스킬·플러그인 그대로)로 실행했다.
  • before는 v0.6.1 그대로, after는 같은 fixture에 이번 템플릿 변경분(13개 파일)만 덮어쓴 것이다. 시나리오마다 설정별로 두 번씩 돌렸다.
  • 채점 기준(시나리오마다 그 단계에서 불려야 할 스킬 목록, 모두 55개 항목)은 개선하기 전에 고정했다. 로그에서 Skill 도구 호출, 스킬 폴더 파일 읽기(Read·cat·grep), CLI 사용(ego-browser, /_next/mcp, impeccable 스크립트), 에이전트 호출을 뽑아 대조했다. 서브에이전트 안의 호출도 센다.
  • 정적 지표는 두 템플릿의 지침 문서(AGENTS.md, CLAUDE.md, dev-workflow, bts-* 스킬, 에이전트)를 스크립트로 훑어, 설치된 공식 스킬마다 dev-cycle 행에 이름이 나오는지(T3), 라우팅 표·에이전트에만 있는지(T2), 본문 언급뿐인지(T1), 연결이 없는지(T0)를 셌다.

찾은 결함

로드 불가

bts-skills-update가 Skill 도구로 로드되지 않았다

본문의 예시 문구 `` !`명령` ``를 Claude Code가 로드 시점 셸 명령으로 실행했다. dev-cycle 시작 때 외부 스킬 업데이트 알림이 오면 이 스킬로 가게 되어 있는데, 그 경로가 막혀 있었다. 문구를 바꾸고, bts 스킬 본문에 느낌표+백틱이 들어가면 실패하는 테스트를 넣었다. after fixture에서 정상 로드를 확인했다.

Shell command failed for pattern "!`명령`": [stderr]
(eval):1: command not found: 명령
로드 불가

공식 shadcn 스킬이 모노레포 루트에서 로드되지 않는다

스킬이 로드될 때 루트에서 npx shadcn@latest info --json을 실행하는데, BTS 모노레포 루트라 실패한다. 그래서 B 라운드의 shadcn은 Skill 도구로는 쓸 수 없었다. 외부 스킬 스크립트는 고치지 않고, bts-ui와 CLAUDE.md가 .agents/skills/shadcn/SKILL.md를 읽게 했다.

다른 판 로드

전역 스킬이 프로젝트에 고정한 공식 스킬을 가린다

Claude Code의 Skill 도구는 같은 이름이면 개인 스킬(~/.claude/skills)을 먼저 불러온다. 이 기기에서는 프로젝트 도메인 스킬 34개 가운데 12개(impeccable, next-dev-loop, supabase-postgres-best-practices, vercel-react-best-practices, web-design-guidelines, agent-browser 등)가 가려져, 템플릿이 고정하고 검증한 판 대신 전역 판이 로드됐다. 외부 스킬은 프로젝트 경로로 읽도록 AGENTS.md, CLAUDE.md, 에이전트에 적었다.


      

    

  


  

    
무엇을 고쳤나

    
원칙은 두 가지다. before run에서 행 문구에 이름이 있는 스킬은 거의 항상 불렸고, 계층 스킬의 "공식 스킬 연결" 표에만 있는 스킬은 대부분 무시됐다. 그래서 그 상황이 오는 행에 스킬 이름을 넣고, 증거 칸에 읽은 스킬을 적게 했다.

    

      
E 행 전: 스키마 수정 + dbGenerate, 생성 SQL 검토 (bts-db) → 마이그레이션 파일 경로와 요약

      
E 행 후: 스키마 수정 + dbGenerate, 생성 SQL 검토 (bts-db, 컬럼 타입·제약·인덱스는 supabase-postgres-best-practices) → 마이그레이션 파일 경로와 요약, 사용한 스킬

    

    

      
파일바꾼 내용근거가 된 before 관찰

      
        
docs/dev-workflow.md (두 템플릿)B 구현 행에 shadcn·vercel-react-best-practices, B audit 행에 web-design-guidelines, D 구현 행에 test-driven-development·better-auth-best-practices, E 행에 supabase-postgres-best-practices와 neon-postgres-branches(supabase는 supabase 스킬 체크리스트), F 계획 행에 "바꿀 계층의 bts-*와 공식 스킬 연결 표", 공통 문서 행에 domain-modeling 형식B의 shadcn·vercel-react-best-practices 0/2, D의 test-driven-development·turborepo 0/2, F의 supabase-postgres-best-practices 0/2·bts-web 1/2, 인증의 better-auth-best-practices·email-and-password-best-practices 0/2

        
bts-dev-cycle (두 템플릿)첫 증거 전에 bts-verify 불러오기, 새 용어는 domain-modeling 형식, 괄호 안 스킬을 외부 스킬까지 넓힘, turbo.json은 turborepo 번들 문서, 확인 전 verification-before-completion, 리뷰 응답 skills_read 확인E에서 bts-verify를 읽지 않아 금지된 git stash로 lint 기준을 비교, domain-modeling 0/2, verification-before-completion 0/2

        
AGENTS.md, CLAUDE.mdbts-*가 가리키는 외부 스킬은 그 상황에서 실제로 읽고, 프로젝트 판 .agents/skills/<이름>/SKILL.md를 읽으며, 행 증거에 적는다. Claude Code는 Skill 도구 대신 Read프로젝트에 설치된 외부 스킬 로드 19건 중 11건이 전역 판, shadcn 로드 실패

        
bts-reviewer, bts-implementer리뷰어: 외부 스킬은 프로젝트 경로로 읽고 React 코드면 vercel-react-best-practices, 응답 JSON에 skills_read. 구현자: 지정 스킬의 공식 스킬 연결 표에서 해당 스킬을 읽고 보고에 "읽은 스킬"db 리뷰어가 절차 1의 supabase-postgres-best-practices를 읽지 않음

        
bts-web느림·깜빡임·번들·캐시·프리패치는 분석 전에 vercel-react-best-practices와 해당 Next 스킬을 읽고 규칙 이름을 붙이며, 동작은 next-dev-loop로 본다성능 분석이 공식 스킬 4종을 하나도 읽지 않음(1/7)

        
bts-ui, impeccable-map.mdshadcn과 impeccable을 프로젝트 경로로 읽는다shadcn 로드 실패, impeccable 전역 판 로드

        
bts-skills-update, bts-deploy느낌표+백틱 문구 제거. bts-deploy는 준비 확인 때 migration-flow 배포 환경 절을 읽는다고 명시bts-skills-update 로드 실패

        
bts-verify, evidence.md외부 스킬을 읽었으면 적용한 규칙과 함께 증거에 적는다증거 칸에 외부 스킬 흔적이 없어 사후 확인이 어려움

        
테스트skills.test.mjs에 느낌표+백틱 금지, template-docs.test.mjs에 스킬 연결 회귀 검사. 둘 다 before 판에서 실패, 지금 판에서 통과(두 템플릿 157/157)

      
    

  


  

    
정적 연결 지표

    
설치된 공식 도메인 스킬이 지침 문서 어디에 연결되어 있는지 스크립트로 셌다. T3는 dev-cycle 행에 이름이 나오는 스킬, T2는 라우팅 표나 에이전트에만 있는 스킬, T1은 본문 언급뿐, T0은 연결 없음이다.

    

    
T0로 남은 grilling은 grill-with-docs가 안에서 부르는 의존 스킬이다. 프로세스 스킬 가운데 연결이 없는 6개(using-superpowers, requesting-code-review 등)는 Codex용 superpowers 묶음에 딸린 것으로, superpowers 스킬끼리 부른다.

  


  

    
비용과 시간

    

    

    
run 한 번의 평균. 비용은 claude -p가 보고한 API 환산값(서브에이전트 포함), 시간은 실제 경과 시간이다.

  


  

    
시나리오별 세부 결과

    

  


  

    
한계

    
    
      
  • 설정마다 run이 두 번뿐이다. F 스펙·계획은 before 두 run이 11/12와 9/12로 갈렸다. 차이가 한 항목 안팎인 시나리오는 편차로 본다.
    • 
      
  • 채점 기준은 제가 정했다. 개선 전에 고정했고 before와 after에 똑같이 적용했지만, 어떤 스킬이 "그 단계에서 불려야 하는지"는 판단이 들어간다. 성능 분석 요청에 dev-cycle 라운드를 기대한 항목은 해석이 갈릴 수 있다(요청이 "고쳐 줘"가 아니라 "개선안 정리"였다).
    • 
      
  • 배포 준비 시나리오는 before도 3/3이라 개선을 가르지 못했다.
    • 
      
  • 이 기기 하나(전역 스킬과 플러그인이 많은 환경)에서만 쟀다. 전역 스킬이 없는 팀원 환경에서는 전역 판 가림 문제가 없고, before 점수가 다를 수 있다.
    • 
      
  • before 인증 run-1과 B run-2는 같은 시간대에 같은 웹 포트(3401)를 썼다. 스킬 호출 측정에는 영향이 없지만 화면 검증의 품질 비교에는 쓰지 않았다.
    • 
      
  • 측정은 neon 템플릿으로만 했다. supabase 템플릿은 같은 변경을 넣었고(E 행은 supabase 문구) 테스트는 통과했지만, 동작 run은 돌리지 않았다.
    • 
      
  • 스킬을 "읽었는지"를 셌지, 읽은 내용을 제대로 적용했는지는 채점하지 않았다. 적용 품질은 증거 칸과 최종 보고로 일부만 확인했다(예: after E의 enum 선택 근거, after D의 turbo 번들 문서 인용).
