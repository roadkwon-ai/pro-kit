# 튜토리얼 로드맵

설계: [튜토리얼 교재 설계](../specs/2026-10-01-bts-starter-kit-tutorials-design.md)
작업공간: `../bts-samples/tutorials/` (저장소 밖)

참고할 자료(모두 저장소 밖의 영구 폴더. 재부팅해도 남는다):
- 기존 샘플 8개 프로젝트: `../bts-samples/ws/<샘플>/`(`PRODUCT.md`, `DESIGN.md`, `GLOSSARY.md`, `docs/briefs/`, 코드). 14번의 원본
- 샘플을 만들 때 쓴 프롬프트와 실행 기록: `../bts-samples/prompts/`, `../bts-samples/logs/`(`<샘플>-R6` 등), `ws/replay-<샘플>.log`
- 포트폴리오 사이트: `../bts-samples/ws/portfolio/`(`docs/briefs/site-map.md`, `tools/export.sh`, `tools/publish-root.sh`)
- 2026-10-01 세션 임시 폴더 복사본: `../bts-samples/notes/2026-10-01-scratchpad/`(넷플릭스 참고 화면 `ref-netflix/`, 스타일 카탈로그 조사 `aw_*`·`kr_*`, 시안 프롬프트 `comp-prompts/`, 화면 검사 스크립트 `qa/`)

서비스마다 기획·설계 → **사용자 승인** → 교재와 프롬프트 → 샘플 페이지(기능 없음) → 교재 마무리 → 검수 → 사이트 반영 순서로 한다(설계 6절). 교재를 끝까지 실행해 만들지는 않는다. 세션이 바뀌면 이 표의 상태부터 확인한다.

**진행 순서(2026-10-01 사용자 결정)**: 14번(기존 샘플 8개 교재와 튜토리얼 페이지)을 먼저 끝낸 뒤 1번부터 하나씩 차례로 한다. 14번은 2026-10-02에 시작한다.

## 효율 규칙 (2026-10-02 사용자 지시)

"퀄리티를 결정하는 중요한부분들은 절대 단축시키면 안되고 그외 효율적으로 시간을 단축시킬 수 있는 부분들은 개선을 통해 단축". 14번 시범(교재 40분, R3 40분, R4 80~100분)에서 시간이 샌 곳을 근거로 정했다.

**줄이지 않는 것 (품질)**
- 사실 확인: 샘플 수치, 이름, 만든 과정은 근거(`samples.json`, 샘플 `PRODUCT.md`, `VERIFICATION.md`, 세션 기록)와 대조한다.
- 교재 독립 검토(사실·절차) 1회, korean-skills 세 스킬.
- bts-ui 절차: 사용자 결정 지점, 시안 대조 게이트, critique·audit·web-design-guidelines → polish → 재확인, 링크·버튼 전수 검사, 코드 리뷰.
- bts-starter-kit 수정: 두 템플릿 테스트와 실제 설치 확인.

**줄이는 것 (낭비)**
1. 내용 먼저, 사이트 라운드는 나중: 교재 원본을 다 쓰고 검토까지 마친 뒤 사이트 라운드를 연다. R3는 원본이 바뀌는 중에 돌아 고른 시안 3장을 다시 그리고 검증 에이전트를 두 번 더 돌렸다.
2. 사이트 틀은 다시 설계하지 않는다: 샘플 쪽과 새 교재는 `pnpm tutorials:sync` → 빌드 → 내보내기만 한다. 새 블록 모양이 필요할 때만 좁은 개선으로 한다(구조 뽑기·시안 없음).
3. 헤드리스 라운드는 이어 간다: 같은 기능의 다음 라운드는 `tools/run.sh … <세션 ID>`(`--resume`)로 이어 가서 코드와 브리프를 다시 읽지 않게 한다. R4는 처음 15분을 다시 읽는 데 썼다. 프롬프트에는 바뀐 점과 읽을 파일만 적는다. 2026-10-03 측정: 같은 세션을 R14 → R15 → R16 → R16 보강으로 네 번 이어 쓰자, 호출 한 번의 평균 문맥이 177k → 374k → 558k → 652k 토큰으로 커졌다. 턴당 비용도 $0.08 → $0.21 → $0.50 → $1.27로 늘었다(R16 보강은 33분에 $62.36). 이어 가기는 바로 다음 라운드까지만 하고, 그다음은 새 세션에 직전 보고와 바뀐 점만 준다.
4. 검사 도구를 다시 쓴다: 화면 찍기와 링크·버튼 검사는 `../bts-samples/tools/`의 `capture.mjs`, `site-check.mjs`, `ui-audit.mjs`, `root-check.mjs`를 쓰게 한다. 라운드마다 새 도우미를 만들지 않는다(R4는 Playwright 도우미를 새로 만들었다). 2026-10-03 점검: 이 규칙이 라운드 프롬프트에 들어가지 않아 R5~R14가 검사 스크립트 53개(3,272줄)를 새로 쓰고 고치며 다시 돌렸다(R10·R11·R14 화면 찍기·검사 12~15분). 되풀이한 검사를 `tools/qa.mjs`(widths, axe, clean, shots)로 모으고 `tools/README.md`에 도구 안내를 쓰고, `run.sh`가 모든 라운드 프롬프트 끝에 `prompts/_footer.txt`(도구를 먼저 쓰라는 안내)를 붙이게 했다. axe-core는 R4부터 쓴 4.10.3을 `tools/node_modules`에 고정했다(전에는 재부팅 때 지워지는 `/tmp/axe`). 확인: `qa.mjs widths`로 R14 조건(쪽 3개 × 너비 18개)을 다시 재니 헤더 높이, 로고·메뉴·GitHub·푸터 로고 줄 수, 헤더·쪽 넘침 54행이 R14 `header-after.json`과 모두 같았다(48초). R15 측정(`round-timing.py`가 `qa.mjs`·라운드 스크립트를 "화면 검사"로 따로 세게 고침): 74분 중 공용 도구 25.7분, 라운드 스크립트 19.1분(새 스크립트 7개 810줄: 기준 코드 복제·재현, 경계 폭 키보드 동작, 픽셀 비교, preload 기록, 확대 창). 검사 범위가 R14보다 넓어 시간은 줄지 않았다. 되풀이되면 도구로 옮길 후보: 기준 커밋 복제·빌드·띄우기, 메뉴 키보드 순회. `qa.mjs clean`은 마지막 대기를 0.8초에서 3.5초로 늘렸다(preload 미사용 경고가 약 3초 뒤에 나와 놓쳤다).
5. 사실은 JSON 한 파일로 모은다: 샘플 쪽의 사실(수치, 추천 1~3위, 고른 시안, 이름·헤드라인 변화, 다시 만든 사진, 실전 데이터·외부 서비스)은 `../bts-samples/notes/sample-facts.json`(2026-10-02 작성, 샘플 8개, 고루만 `verified: true`)에 두고 쪽은 이 값과 `goru.md`의 절 순서로 쓴다. 2026-10-03 점검: 샘플 쪽 7개를 쓸 때 실제로 썼지만(에이전트가 빈 값과 다른 값을 근거대로 바로잡음) 결과를 되돌려 적지 않아 7개가 `verified: false`로 남았고, 쪽 작성 지침은 scratchpad에 있어 지워졌다. 지침을 `../bts-samples/notes/sample-page-brief.md`로 되살리고(포트폴리오 이름, 검수 표현 반영, 끝나면 JSON을 갱신하는 단계 추가), 8개 항목을 쪽과 대조해 키 구성을 맞추고 모두 `verified: true`로 바꿨다(수치는 `samples.json`과 스크립트로 대조해 0건 다름). 수치는 포트폴리오 `samples.json`에서 스크립트로 채운다. 근거가 더 필요하면 스크립트로 모은다: 세션 기록의 사용자 요청은 `tools/usermsgs.py <세션 폴더>`로 뽑아 필요한 줄만 읽는다. 기록 전체를 읽지 않는다.
6. 묶어서 한 번에: 샘플 쪽 7개는 한 번에 쓴다. 독립 검토, korean-skills, 내보내기와 사이트 확인도 마지막에 한 번씩 한다.
7. 대조표 증거는 한두 줄로, 경로와 숫자 위주로 쓴다.
8. 시안과 스크린샷은 1200px JPEG로 줄여서 본다.
9. 기계적인 일(가져오기, 빌드, 내보내기, 링크 검사)은 에이전트가 아니라 스크립트로 돌린다.

**메모리 DB 검토 (2026-10-02, 도입하지 않음)**: 사용자 제안으로 측정했다.
- 시간이 든 곳(세션 기록의 타임스탬프로 계산): R2 85분 중 모델(생각·글쓰기) 41분, 서브에이전트 리뷰 17분, 화면 찍기 15분, 시안 대조 5분, 파일 읽기 0.3분. R3 40분 중 모델 27분, 파일 읽기 0.1분. R4는 51분 시점에 모델 32분, 파일 읽기 0.1분. 데이터를 읽고 찾는 시간은 1%도 안 된다.
- 세션 기록 검색(48개 파일, 906MB): 매번 훑기 2.15초, SQLite FTS5(메모리) 색인 만들기 2.09초 뒤 검색 0.1ms. 교재 하나에서 검색은 열 번 남짓이라 아끼는 시간은 30초 안팎이다. 돌려주는 줄이 같아서 토큰도 줄지 않는다.
- RAG·그래프 DB(같은 날 추가 검토, 도입하지 않음): 라운드 토큰은 턴 수 × 맥락 크기다(R4 217턴, 캐시 읽기 94M 토큰, R2 427턴 146M). 도구로 읽어 들인 글은 라운드당 50만~100만 자이고, 그중 큰 덩어리는 impeccable 참조 문서(약 8만 자)와 코드·브리프다. 절차 문서는 빠짐없이 읽어야 규칙을 지키므로 조각만 찾아 읽는 RAG는 품질 규칙과 맞지 않고, 줄일 수 있는 양도 맥락 전체에 비해 작다. 사실 묶음은 이미 손으로 정리한 표(설계 7절, `samples.json`)가 가장 단순하고 정확하다. 이미 있는 도구(graphify, OMC wiki·project memory)도 더하지 않는다.
- 결론: 병목은 모델이 처리하는 양(턴 수, 다시 읽는 맥락, 긴 출력)이지 저장소가 아니다. 위 1·3·7번(내용 먼저, 세션 이어 가기, 짧은 증거)이 이 병목을 줄인다. 라운드 시간 측정은 `../bts-samples/tools/round-timing.py`로 다시 잴 수 있다(저장소에는 넣지 않는다).
