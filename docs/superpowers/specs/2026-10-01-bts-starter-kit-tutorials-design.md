# bts-starter-kit 튜토리얼 교재 설계 (유명 서비스 13개 본뜨기)

작성일: 2026-10-01
상태: 대화에서 방향 승인("진행해줘"). 2026-10-01 범위 조정: 교재를 끝까지 실행해 만들지 않고 기획·설계, 교재와 프롬프트, 기능 없는 샘플 페이지만 만든다. 서비스별 기획은 각자 승인을 받는다.
할 일 목록: [튜토리얼 로드맵](../plans/2026-10-01-tutorials-roadmap.md)

## 1. 목표와 독자

비개발자와 AI 개발 초보자가 bts-starter-kit만으로 유명 서비스를 닮은 연습용 서비스를 끝까지 만들어 보게 한다. 독자는 프롬프트를 복사해 Claude Code나 Codex에 붙여 넣으며 장을 따라간다.

성공 기준:
- 교재의 프롬프트가 bts-starter-kit 절차(`AGENTS.md`의 생성 절차, `bts-ui`, `bts-dev-cycle`)와 어긋나지 않는다. 교재를 끝까지 실행해 확인하지는 않는다(2026-10-01 사용자 결정: 시간과 토큰 절약). 교재 표지에 이 확인 범위를 밝힌다.
- 교재마다 완성 화면을 보여 주는 샘플 사이트(기능 없는 정적 화면)가 모아 보기 사이트에 있다.
- 본문에 설명 없는 전문 용어가 없다. 어려운 내용은 `tutorials/reference/`로 보낸다.
- 모든 글이 korean-skills 검수(humanizer → style-guide → grammar-checker)를 거쳤다.

## 3. 본뜨기 원칙

- **이름**: 원래 서비스 이름을 살짝 바꾼 이름을 쓴다(예: 넷플릭스 → Nextflix). 2026-10-01 사용자 결정. 기획 단계에서 후보 3개를 내고 사용자가 고른다. 교재 제목에는 "넷플릭스 같은 영상 구독 서비스 만들기"처럼 원래 서비스를 밝힌다. 이름이 비슷한 만큼 아래 디자인, 안내 문구, 입력값 규칙을 반드시 지킨다.
- **디자인**: 레이아웃, 화면 흐름, 컴포넌트 배치, 인터랙션, 밀도, 색의 분위기는 원래 서비스와 거의 같게 만든다(2026-10-01 사용자 결정). 디자인 카탈로그 세 곳(getdesign.kr, awesome-design-md(getdesign.md), Refero Styles)을 `bts-ui` 절차(`references/impeccable-map.md` "디자인 카탈로그에서 고르기")로 모두 찾아보고, 원래 서비스의 DESIGN.md가 있으면 구조의 기준으로 쓴다(2026-10-05 사용자 지적으로 Refero만 보던 것을 고침). Refero 원문은 페이지의 다운로드 버튼으로 받는다. 같은 브랜드의 스타일이 여럿이면 모두 받아 기준 화면과 추출일을 비교한다. 원문은 저장소에 넣지 않고, 독자의 에이전트가 자료 팩의 `design-notes.md`에 적힌 주소에서 받아 그 파일대로 고쳐 쓰게 한다(3-1절). 다만 브랜드를 알아보게 하는 요소는 새로 만든다: 로고와 워드마크, 원래 브랜드 색 코드(같은 계열의 다른 색을 쓴다), 전용 서체, 고유 아이콘, 문구, 사진과 영상. 이름까지 비슷한 화면이 공개 주소에 올라가므로, 진짜 서비스나 피싱 화면으로 오인되지 않게 하는 최소한의 차이다.
- **안내 문구**: 샘플 사이트 푸터와 교재 표지에 "OO와 관계없는 연습용 서비스예요. 데이터는 모두 예시예요."를 둔다. 로그인, 결제, 송금 화면이 있는 샘플(쿠팡, 토스, 배달의민족 등)은 화면 위에 연습용 띠를 따로 둔다.
- **값을 받지 않는다**: 로그인, 결제, 송금 화면은 샘플에서 정적 화면이다. 입력값을 어디에도 보내지 않는다.
- **참고 서비스 분석**: 공개 페이지와 ego browser(lilys.ai, vooster.ai, 인프런은 로그인 상태)로 메뉴, 화면 흐름, 기능 목록만 읽는다. 글쓰기, 결제, 설정 변경, 업로드처럼 계정에 흔적이 남는 동작은 하지 않는다. 분석 결과는 기능 목록으로만 남기고 원문을 옮기지 않는다.
- **교재 프롬프트**: 색, 크기 같은 값을 넣지 않고 자료 팩을 가리킨다(3-1절). 독자의 에이전트에게 원래 서비스를 다시 조사하게 하지 않는다. 우리가 잰 값은 팩, 샘플 제작, 교재의 "이렇게 되면 성공" 확인 항목에 쓴다.
- **외부 연결**: 영상은 공개 라이선스 영상이나 AI로 만든 포스터를 쓴다. 지도, 실제 결제, 송금, 외부 API는 화면만 만들고 실제 연결 방법은 참고 자료로 보낸다. AI 기능은 키가 있으면 실제 호출, 없으면 모의 응답으로 끝까지 따라갈 수 있게 한다.

## 3-1. 자료 팩 (2026-10-05 사용자 결정)

독자는 리서치하지 않는다. 교재를 만드는 쪽이 원래 서비스를 한 번 조사해 자료 팩으로 묶고, 독자의 에이전트는 팩만 보고 만든다. 독자는 조사 시간과 준비물(원래 서비스 계정, ego lite) 없이 바로 시작하고, 이름만 바꿔 자기 서비스로 만들어 볼 수 있다.

| 자료 | 위치 | 내용 |
|---|---|---|
| `design-notes.md` | `tutorials/<번호>-<slug>/pack/` | DESIGN.md를 받을 카탈로그 주소(Refero는 스타일 페이지, awesome-design-md는 GitHub 원문 주소. 조사 때 확인한 스타일 id와 추출일)와, 받은 원문 위에 고칠 것: 실제로 만들 화면 기준 값(예: 원문이 로그인 전 랜딩 기준이면 로그인 후 화면의 배경, 반경, 버튼 모양)과 브랜드 대체(같은 계열의 다른 색, 공개 서체, 글자 로고). 원문은 독자의 에이전트가 튜토리얼을 진행할 때 받는다(2026-10-05 사용자 결정) |
| `screens.md` | 같은 곳 | 사이트맵, 화면별 구성(위에서 아래 순서), 인터랙션, 반응형 기준, 빈 상태 |
| `features.md` | 같은 곳 | 기능 장에 쓸 규칙(개수 제한, 상태, 예외)과 데이터 모델 힌트 |
| `data/` | 같은 곳 | 예시 데이터(JSON). 작품·사람 이름은 모두 가상. 공개 영상 주소와 저작자 표기 |
| `wireframes/` | 같은 곳 | 우리가 그린 화면 배치도(SVG, 치수 표시) |
| `images.json` | 같은 곳 | 이미지 묶음의 주소와 파일 목록 |
| `SOURCES.md` | 같은 곳 | 조사 날짜, 출처 링크, 라이선스(팩은 저장소 라이선스, 영상은 원래 라이선스와 표기 문구) |
| 이미지 묶음 | GitHub Release 첨부 `<slug>-images.zip` | AI로 만든 포스터, 카드, 빌보드, 아바타(webp). 팩 전용 릴리스(태그 `pack-<slug>-<판>`, `v*` 릴리스와 따로, GitHub "Latest" 표시 안 함)에 올려 교재에 적은 주소가 판이 바뀌기 전까지 그대로 가게 한다. 저장소 크기를 늘리지 않기 위해 `main`에는 넣지 않는다 |

- **팩에 넣지 않는 것**: 디자인 카탈로그 원문(Refero 이용 약관 10절이 Refero 콘텐츠의 재배포와 단독 라이브러리·데이터셋 공개를 금지한다. 독자가 자기 디자인 작업에 쓰려고 직접 받는 것은 허용되므로 주소만 두고 튜토리얼 진행 때 받게 한다), 원래 서비스의 스크린샷, 로고, 작품 이미지, 문구. 이런 참고 자료는 저장소 밖 작업공간(`../bts-samples/research/<slug>/`)에만 둔다.
- **이름 바꾸기 쉽게**: 서비스 이름은 팩 안 한 값으로 쓰고 로고는 글자로 만든다. 독자가 "이름은 OO로 해줘" 한 줄로 바꿀 수 있게 한다.
- **팩 검증**: 샘플 사이트를 팩만으로 만든다(6절 4번). 팩만으로 되지 않는 곳이 나오면 팩을 고친다.
- **선택 팁**: 더 똑같이 맞추고 싶은 독자에게는 ego lite에 로그인해 둔 원래 서비스를 에이전트가 직접 보고 맞추게 하는 프롬프트를 팁으로 준다(읽기만, 재생·찜·평가·글쓰기·설정 변경 금지, 계정 정보 캡처 금지). 기본 흐름에는 넣지 않는다.

## 4. 저장소 구성 (`main`)

```
tutorials/
├── README.md               튜토리얼 안내. 완성된 교재만 싣는다
├── start/README.md         시작하기 (모든 교재의 1장 전에 한 번)
├── reference/              참고 자료 (용어, 막혔을 때, Claude Code와 Codex, 비용과 키, Windows)
├── <번호>-<이름>/           교재 한 권. 이름은 기획에서 정한 서비스 slug
│   ├── README.md           표지: 무엇을 만드나, 원래 서비스, 샘플 링크, 시간과 비용, 장 목록
│   ├── 01-<주제>.md …      장
│   ├── assets/             스크린샷(.webp), 도식(.svg와 .png)
│   └── pack/               자료 팩(3-1절): design-notes.md, screens.md, features.md, data/, wireframes/, images.json, SOURCES.md
└── samples/                기존 샘플 8개 따라 만들기
```

## 5. 교재 형식

### 5.1 권 구성
서비스마다 기능 장은 달라도 뼈대는 같다.

| 장 | 내용 | 결과 |
|---|---|---|
| 1 | 프로젝트 만들기 | bts-starter-kit 폴더에서 "neon 템플릿으로 <이름> 프로젝트 만들어줘" |
| 2 | 서비스 기획 | 자료 팩의 `screens.md`, `features.md`로 `PRODUCT.md`, `GLOSSARY.md`, 사이트맵을 채운다 |
| 3 | 디자인 정하기 | 자료 팩 `design-notes.md`의 카탈로그 주소에서 DESIGN.md를 받아 그 파일대로 고치고 comp 3장. 다른 스타일로 바꾸는 법(카탈로그 추천 1~3위)은 팁으로 둔다 |
| 4 | 모든 화면 만들기 | 자료 팩의 예시 데이터와 이미지로 사이트맵의 모든 페이지. 갤러리 샘플이 이 장의 완성 예시다 |
| 5~ | 기능 장 | 로그인, DB 저장, 서비스 핵심 기능, 대시보드 숫자를 실제 데이터로 |
| 끝-1 | 검사와 다듬기 | "지금까지 만든 거 검증해줘", critique·polish |
| 끝 | 배포 (선택) | Vercel 배포 준비와 배포. 계정이 필요하다고 밝힌다 |

neon 템플릿을 쓴다(Supabase CLI, `DOCKER_HOST`, RLS 단계가 없다). supabase로 하는 법은 참고 자료로 보낸다.

### 5.2 장 형식
1. **이번 장에서 할 일**: 한두 문장과 완성 화면 한 장
2. 단계마다:
   - 할 일 한 문장
   - 프롬프트 블록
   - **이렇게 되면 성공**: 스크린샷이나 확인할 것 2~3개
   - `<details><summary>막히면</summary>`: 흔한 증상과 붙여 넣을 복구 프롬프트, 참고 자료 링크
3. **에이전트가 물어보면**: 이 장에서 나오는 질문과 고를 답
4. 다음 장 링크

### 5.3 블록 규칙
- ```` ```prompt ````: 에이전트 대화창에 붙여 넣는 프롬프트. Claude Code와 Codex에 똑같이 쓴다.
- ```` ```prompt claude ````와 ```` ```prompt codex ````: 두 에이전트가 다를 때만 나란히 둔다.
- ```` ```bash ````: 터미널 명령. 앞에 "터미널에 입력"을 쓴다.
- 알림은 GitHub 알림 문법(`> [!TIP]`, `> [!NOTE]`, `> [!WARNING]`)을 쓴다.
- 프롬프트는 평소 말로 쓰고 스킬 이름이나 파일 경로를 외우게 하지 않는다. 한 블록은 10줄을 넘기지 않는다. 서비스 소개처럼 긴 재료는 교재에 따로 두고 "아래 소개를 붙여 넣어"로 이어 붙인다.

### 5.4 문체
- 해요체. 문장은 짧게, 한 문단은 세 문장 이내.
- 처음 나오는 용어는 괄호로 한 번 풀고 `reference/glossary.md`에 링크한다. 본문에 꼭 필요하지 않은 용어는 쓰지 않는다.
- 번역투, 명사 나열, 과장된 유행어를 쓰지 않는다. 같은 대상은 같은 말로 부른다(예: "에이전트", "대화창", "터미널").

### 5.5 시간과 비용 (2026-10-05 추가)
- 교재 첫 쪽(샘플은 샘플 쪽)에 "## 시간과 비용" 절을 둔다. 모양은 [튜토리얼 프롬프트 설계](2026-10-05-tutorial-prompts-home-and-cost-design.md) 5절을 따른다: 요약(최소 시간과 비용, Claude Pro·ChatGPT Plus 표시, 2~3배 안내), 접힌 "단계별 예상", 접힌 "만든 사람이 실제로 쓴 값".
- 값은 프롬프트와 자료 팩으로 순조롭게 끝날 때의 최소값이다. 단가와 계산법은 같은 설계 6절, 구독 표시는 7절이다. 실측이 있으면 실측을 쓰고, 예상은 칸마다 "예상"이라고 밝힌다.
- 클론 교재는 첫 쪽 위쪽에 토큰 경고를 두고, 요약을 "화면까지"와 "끝까지" 두 줄로 쓴다.
- 겉에 보이는 값은 토큰(캐시 다시 읽기를 뺀 값, 괄호에 캐시 포함)으로 쓰고, 달러는 접힌 표에만 쓴다(같은 설계 5.2절).

## 6. 서비스별 순환

1. **기획·설계**: 원래 서비스의 화면과 흐름을 참고 사이트(모바일은 [wwit.design](https://wwit.design/), 데스크톱은 [Refero Styles](https://styles.refero.design/))와 실제 사이트에서 살펴본다. DESIGN.md는 3절에 적은 대로 카탈로그 세 곳([getdesign.kr](https://www.getdesign.kr), [getdesign.md](https://getdesign.md), [Refero Styles](https://styles.refero.design/))을 모두 찾아보고, 카탈로그마다 찾은 결과(없음 포함)를 기획안에 적는다. 범위(넣을 것과 뺄 것), 사이트맵, 기능 장 목록, 샘플에 쓸 스타일, 이름 후보 3개를 낸다. 리서치는 작업공간 `../bts-samples/research/<slug>/`에 두고 끝에 화면 구성 요약을 쓴다. **사용자 승인을 받는다.**
2. **자료 팩**: 리서치를 3-1절의 팩으로 묶는다. `design-notes.md`에 카탈로그 주소와 고칠 것을 쓰고, 그 주소에서 원문을 받아 고친 결과가 명세 lint를 통과하는지 한 번 확인한다. 예시 데이터와 이미지(8절)를 만들고, 배치도를 그린다. 팩에 넣지 않는 것(카탈로그 원문, 원래 서비스 이미지)이 섞이지 않았는지 본다.
3. **교재와 프롬프트**: 설계대로 장을 쓴다. 프롬프트는 자료 팩을 가리키고, bts-starter-kit 절차와 대조해 쓰며 실행해 보지는 않는다.
4. **샘플 페이지**: 저장소 밖 작업공간(`../bts-samples/tutorials/<slug>`, `bts-samples/base` 복사본)에서 **자료 팩만으로** 사이트맵의 모든 페이지를 예시 데이터로 만든다. 팩만으로 안 되는 곳은 팩을 고친다. 기능(로그인, 저장, 결제)은 구현하지 않는다. 링크와 버튼은 모두 동작해야 한다. 정적 사이트로 내보내 gh-pages `<slug>/`에 둔다(`export.sh`).
5. **교재 마무리**: 샘플 화면의 스크린샷과 도식을 넣는다.
6. **검수**: writing-quality-editor로 쓰고 다듬은 뒤 파일마다 korean-skills 세 스킬을 차례로 적용한다.
7. **사이트 반영**: 허브, 표지, 장 페이지, 갤러리를 갱신해 gh-pages에 올리고, 이미지 묶음을 팩 릴리스로 올린다(push와 릴리스는 요청을 받고).

## 7. 사이트 (모아 보기 사이트에 추가)

- `/tutorials/`: "무엇을 만들어 볼까요?" 교재 카드(완성 화면, 원래 서비스, 단계, 시간), "처음이라면 여기부터"(시작하기), 샘플 따라 만들기
- `/tutorials/start/`, `/tutorials/reference/<쪽>/`
- `/tutorials/<slug>/`: 교재 표지
- `/tutorials/<slug>/<장>/`: 장 페이지. 데스크톱은 왼쪽 장 목록, 모바일은 시트. 프롬프트 카드(복사 버튼, Claude Code/Codex 탭, 고른 탭 기억), 진행 체크(브라우저 저장), 이전·다음 장
- `/tutorials/samples/<샘플>/`: 샘플 가이드
- 기존 화면: 헤더 "튜토리얼" 메뉴, 샘플 상세의 "이 샘플 만들어 보기", 홈의 "유명 서비스 클론하기" 묶음
- 홈 대제목은 "튜토리얼 프롬프트", 묶음은 "컨셉으로 화면 만들기"(샘플)와 "유명 서비스 클론하기"(클론 교재)다(2026-10-05). 클론 교재가 완성되면 "유명 서비스 클론하기"에 카드를 더한다.
- **마크다운이 원본이다.** 사이트는 빌드할 때 `tutorials/`를 읽어 HTML로 만든다. ```` ```prompt ````은 프롬프트 카드, `<details>`는 접는 상자, GitHub 알림은 안내 상자가 된다.
- 사이트맵, 브리프, comp는 1번 교재와 함께 bts-ui 절차로 만든다. 완성된 교재만 싣는다. "준비 중" 페이지는 두지 않는다.

## 8. 이미지와 도식

- 스크린샷: 샘플 페이지 화면을 webp로 넣는다(데스크톱 1440, 모바일 390). 1~3장처럼 터미널에서 진행하는 장은 화면 대신 에이전트가 보여 줄 내용을 글로 적는다.
- 도식: svg-infographic으로 그린 SVG 원본과 2배 렌더를 같이 둔다. 사이트는 `assets/`의 webp만 가져가므로 렌더는 2배 PNG를 무손실 webp로 바꿔 `<이름>@2x.webp`로 둔다(2026-10-03). 사이트는 `@2x` 그림을 절반 폭이 원래 크기인 그림으로 보고 휴대폰 크게 보기의 폭을 정한다. 사이트가 따로 그리는 흐름 띠(굵은 글씨 "기획 → … → HTML 내보내기")는 그림으로 다시 그리지 않는다. 도식 속 문장은 writing-quality-editor로 다듬는다. 교재마다 1~2개 이내.
- 생성 이미지: 포스터, 상품 사진처럼 샘플과 자료 팩에 필요한 그림만 OpenAI 이미지로 만든다. 같은 그림을 샘플과 팩이 함께 쓴다. 키는 셸 환경변수 `OPENAI_API_KEY`로만 쓰고 출력이나 파일에 남기지 않는다. 팩의 이미지 묶음은 3-1절대로 GitHub Release에 올린다.

## 9. 검증 기록

교재 표지 끝 "만든 기록"에 작성 날짜, 대조한 bts-starter-kit 판, 샘플이 기능 없는 화면 예시라는 점, 프롬프트를 끝까지 실행해 확인하지 않았다는 점을 적는다. 실제로 실행해 확인한 프롬프트(시작하기 6단계 등)는 날짜와 결과를 따로 적는다.

## 10. 커밋과 배포

- `main`: `tutorials/`, README 링크, 이 문서와 로드맵. 커밋과 push는 요청을 받아 릴리스 절차로 한다.
- gh-pages: 교재 샘플 폴더와 모아 보기 사이트 갱신. push는 요청을 받아 한다.
- GitHub Release: 자료 팩 이미지 묶음(`pack-<slug>-<판>` 태그). 요청을 받아 올린다. 첫 팩을 올릴 때 루트 `AGENTS.md` "버전과 릴리스"와 README "릴리스" 절에 팩 릴리스 방법을 더한다(`v*` 태그와 노트는 기존 절차 그대로).
- 작업공간, 실행 로그, 내보내기 스크립트는 저장소에 넣지 않는다.
