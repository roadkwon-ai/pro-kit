# 진행 계획과 Task

여러 라운드에 걸친 일(기존 프로젝트 도입, 전환, 큰 기능 묶음)을 Task로 나눠 하나씩 끝내는 절차다. Task 하나는 dev-cycle 라운드 하나이고, 앞 Task가 완전히 끝나야 다음 Task 라운드가 열린다(Task 게이트).

## 1. 정밀 분석
기존 프로젝트(`.dev-cycle.json`의 `projectType`이 `early`, `operating`, `migration`)는 계획 전에 `prokit-analyzer`로 정밀 분석을 한다. 입력은 `docs/prokit/intake.md`, PRD·기획 자료, `legacy.path`다. 돌려받은 보고서를 `docs/prokit/analysis.md`에 쓴다. 이 파일은 2절의 계획 라운드(케이스 A)에서 계획 문서와 함께 커밋한다. 분석 점검표와 보고서 틀은 [analysis.md](analysis.md)다.

## 2. 진행 계획 세우기
0. 계획을 쓰기 전에 결과를 바꾸는 질문부터 묻는다. 기존 프로젝트는 정밀 분석의 "먼저 확인할 질문" 가운데 Task 구성을 바꾸는 것, 새 프로젝트는 PRD의 모호함이다. grilling 형식으로 묻고 답을 받은 뒤 계획을 쓴다. 리뷰까지 받은 뒤 물으면 답이 다를 때 계획과 리뷰를 다시 해야 한다.
1. 주 두뇌(없으면 기본 AI)가 계획 방법으로 진행 계획 문서를 쓴다: `docs/plans/<날짜>-<유형>-plan.md`. 목표, 범위, 만들지 않는 것, Task 목록(Task마다 목표, 범위, 완료 조건, 예상 케이스, 위험), 순서의 이유, 되돌리기 방법을 적는다. 두뇌의 계획 경로(`openspec/changes/`, `specs/` 등)를 쓰면 그 경로를 문서에 링크한다.
2. Task 크기: 라운드 하나로 끝나고 사용자가 결과를 확인할 수 있는 크기다. 크면 나눈다. 첫 Task는 대개 H(경로 규칙·하네스 맞추기)다.
3. Task 표를 `tasks/plan.md`에 쓴다. 형식은 아래 그대로다. 제목에 `|`를 쓰지 않는다. 이 파일은 dev-cycle이 읽는다. 두뇌의 계획 도구가 같은 경로에 쓰려 하면(agent-skills `/plan`의 기본값) 그 계획은 `docs/plans/`에 쓰게 한다. `dev-cycle:plan` 블록이 없는 `tasks/plan.md`는 진행 계획으로 보지 않는다.

   ```markdown
   <!-- dev-cycle:plan doc=docs/plans/2026-10-23-migration-plan.md -->
   ## 진행 계획: 레거시 예약 서비스 전환
   | Task | 제목 | 상태 | 기록 |
   |---|---|---|---|
   | T1 | 하네스 경로 규칙 맞추기 | 대기 | |
   | T2 | 회원 데이터 모델 옮기기 | 대기 | |
   <!-- dev-cycle:plan-end -->
   ```

4. 계획 문서와 Task 표는 진행 계획 라운드 하나로 만든다. `pnpm dev-cycle table A --write --title "<요약>" --plan`으로 열면 맨 앞에 정밀 분석(기존 프로젝트만), 계획 문서와 Task 표, `prokit-reviewer(plan)` 계획 리뷰 행이 붙는다. 행을 손으로 더하지 않는다. `[confirm]` 행에서 사용자가 계획을 확인한다. 사용자가 계획을 보기 전에 "진행해"라고 미리 말했어도 리뷰를 반영한 최종 계획의 요약(Task 목록, 바뀐 결정)을 보여 주고 확인받은 뒤 채운다. 리뷰를 반영하다 사용자가 정한 결정이 바뀌면 그 변경을 보여 주고 다시 확인받는다. 계획을 고치는 라운드의 정밀 분석 행에는 기존 `docs/prokit/analysis.md`와 그 뒤 바뀐 것이 없는지(예: 분석 뒤 앱 코드 diff)를 적고, 다시 분석했으면 그 결과를 적는다. 계획을 확인받기 전에는 Task의 산출물(스펙, 브리프, 코드)을 만들지 않는다. audit은 `tasks/plan.md`에 진행 계획 블록이 있는지와 `pnpm dev-cycle plan`의 문제를 본다.

## 3. Task 진행
1. `pnpm dev-cycle plan`이나 `status`로 다음 Task를 본다.
2. `pnpm dev-cycle table <케이스> --write --title "T1 <요약>" --task T1`. 앞 Task가 `완료`나 `제외`가 아니면 열리지 않는다. 앞 라운드를 닫은 뒤 커밋하지 않아 `tasks/plan.md`에 변경(지문, Task 상태)이 남아 있어도 열리지 않는다(`5. 종료`의 커밋). 대조표 맨 앞에 두 행이 붙는다.
   - 세부 계획을 쓰기 전에 그 케이스에서 사용자에게 물을 것(B·F의 디자인 방향·스타일, 결과를 바꾸는 용어·범위 질문)을 먼저 묻고 답을 계획에 반영한다.
   - `[plan] Task 세부 계획`: 진행 계획의 이 Task를 지금 코드 기준으로 다시 설계하고 구체화한다. 바꿀 파일, 단계, 단계별 검사, 완료 조건을 `docs/plans/<날짜>-T1-<주제>.md`(또는 두뇌의 계획 경로)에 쓰고 그 경로를 증거로 적는다. 바꿀 파일이 연 케이스보다 무거운 경로 규칙(`.dev-cycle.json`의 `rules`. 예: `packages/api/`는 D)에 걸리면 구현 전에 `pnpm dev-cycle table <케이스> --write --upgrade`로 올린다.
   - `[review] prokit-reviewer(plan)`: 세부 계획 리뷰다. 바꿀 파일과 연 케이스가 맞는지도 본다. 케이스 행에 계획 리뷰가 이미 있으면(F) 그 행 하나로 한다. F의 구현 계획 행에는 `[plan]` 행과 같은 계획 문서 경로를 써도 된다(계획 문서를 두 번 쓰지 않는다).
3. 나머지 행(구현, 검수, 테스트, 검증, 보완, 사용자 확인)을 지금처럼 채운다. 세부 계획의 단계마다 구현 → 검사 → 리뷰 지적 보완을 끝내고 다음 단계로 간다.
4. `pnpm dev-cycle audit` → `close`. close가 `tasks/plan.md`의 그 Task를 `완료`로 바꾸고 기록 칸에 보관 파일을 더한다. 다음 Task로 간다.

## 4. 상태와 예외
| 상태 | 뜻 | 바꾸는 것 |
|---|---|---|
| 대기 | 아직 시작하지 않음 | 계획을 쓸 때 |
| 진행 | 라운드를 열었거나 부분 완료로 닫음 | `table --task`, `close --partial` |
| 완료 | 라운드가 audit과 사용자 확인을 통과해 닫힘 | `close` |
| 제외 | 사용자가 하지 않기로 정함 | 사용자 결정을 받아 직접 고치고 기록 칸에 `제외: <사유> (사용자, <날짜>)`. 앞 Task가 남아 있어도 적을 수 있다 |

- `close --partial`(blocked·미실행이 남음)은 Task를 `진행`으로 둔다. 같은 Task를 `--task`로 다시 열어 끝낸다. 그동안 다음 Task는 열리지 않는다.
- 손으로 `완료`라고 고치면 `pnpm dev-cycle plan`·`audit`이 잡는다. 완료의 증거는 기록 칸의 마지막 보관 파일이다.
- 진행 계획 라운드를 닫으면(부분 완료 포함) Task 구성(번호·제목·순서)의 지문이 계획 블록 머리에 `sig=`로 적힌다. Task 게이트는 지문이 있는 계획에서만 Task를 연다. 그 뒤 진행 계획 라운드 밖에서 Task를 더하거나 빼거나 제목·순서를 바꾸면 `pnpm dev-cycle plan`·Task 게이트·`audit`이 잡고, Task를 시작한 계획에서 `sig=`를 지워도 잡는다. 다른 라운드가 열려 있을 때 잡히면 먼저 되돌린다(그 라운드를 닫을 수 없다). 상태와 기록 칸(완료, 제외)은 지문에 들지 않는다. `sig=`는 손으로 고치거나 지우지 않는다.
- 진행 중에 생긴 버그 수정이나 하네스 변경은 `--task` 없이 라운드를 열어도 된다. Task를 끝낸 것으로 세지 않는다.
- 계획을 바꿔야 하면(Task를 나누거나 더하거나 순서를 바꿈) 진행 중인 Task를 닫은 뒤 진행 계획 라운드(`--plan`)에서 계획 문서와 Task 표를 고치고 다시 확인받는다. 끝난 Task의 기록은 고치지 않는다.
- 사용자가 앞 Task를 미루거나 건너뛰자고 하면 지시처럼 들려도 바로 고치지 않는다. Task 게이트를 설명하고 고르게 한다: 그 Task를 마저 하기(추천), 제외(그 Task는 하지 않는다. 사유를 받아 기록), 순서 바꾸기(진행 계획 라운드에서 계획 리뷰와 확인을 다시 받는다). 고른 뒤에 바꾼다. Task 표의 순서·제목·범위는 진행 계획 라운드 밖에서 손이나 스크립트로 고치지 않는다.

## 5. 전환(migration) 메모
- 기존 서비스는 끝까지 켜 둔다. 새 프로젝트에서 기능 단위로 옮기고, 아직 옮기지 않은 경로는 기존 서비스로 보내는 방식(Next.js `rewrites`의 fallback 등)을 정밀 분석의 병행 운영 방식으로 정한다.
- 데이터 이전 Task는 이전 방법, 검증 쿼리, 되돌리기 방법을 세부 계획에 적고 운영 데이터는 사용자 동의 뒤에만 다룬다.
- 전환 마지막 Task는 전환 시점(트래픽 전환)과 기존 서비스 종료 조건이다. 사용자 확인 없이 하지 않는다.
