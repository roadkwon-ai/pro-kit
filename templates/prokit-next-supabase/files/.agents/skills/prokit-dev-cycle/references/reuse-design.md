# 재사용과 설정 설계

화면·기능·하네스의 구조를 정할 때 구현 전에 읽는다. 기존 스펙·계획·브리프에 아래 결정을 남긴다. 작은 작업은 대조표 증거 칸에 바로 적는다. `[design]` 증거는 `기존: 경로·소비자; 결정: 재사용·분리 근거; 설정: 환경 변수·설정 영향 또는 변경 없음; 검증: 회귀 검사`로 쓴다. 자세한 판단은 각 항목에 문서 위치를 연결해도 된다. 새 문서나 공통 패키지를 만드는 것이 목표가 아니다.

## 완성팩과 제작 작업의 경계

팩이 있으면 `prokit-pack-use`로 실제 소스를 복원하고 완성 프리셋의 구성·자산·모션·설정을 재사용한다. 원본 URL 재조사나 스타일 재선택으로 팩 구현을 새로 만들지 않는다. 개인화 범위와 API 연결 후 상태별 배치 회귀를 계획에 적는다. 원본 조사·COPY·공식 프리셋 제작은 별도 `pro-kit-preset-skills`가 전담하며 이 템플릿은 맡겨진 기술 구현과 완성팩 활용을 담당한다. 문서 작성·검수는 `pro-kit-docs-skills`로 연결한다.

## 기존 코드와 공통화

요청이 바꾸는 파일과 실제 소비자를 검색한다. 같은 디렉터리에 없더라도 `packages/ui`, 앱의 공통 컴포넌트·유틸, 환경 변수 검증 모듈, 설정 정본을 읽는다. 후보마다 경로와 소비자를 적고 겉모양보다 책임·입출력·변경 이유를 비교한다.

| 결정 | 남길 근거 |
|---|---|
| 그대로 재사용 | 기존 경로·소비자, 이번 요구를 충족하는 부분 |
| 조합·작은 확장 | 기존 계약을 유지하는 변경과 영향받는 소비자 |
| 공통으로 추출 | 함께 바뀌는 실제 반복, 소유 위치, 기존 소비자의 회귀 확인 |
| 별도 구현·보류 | 다른 책임·디자인·변경 주기 또는 현재 소비자 한 곳, 재검토 조건 |

앱 전용 조합은 앱 안에 두고, 여러 소비자가 쓰는 도메인에 독립적인 UI는 기존 `packages/ui` 경계를 따른다. 이름이 비슷하거나 앞으로 쓸 것 같다는 이유만으로 추출하지 않는다. boolean 옵션, wrapper, Provider, 범용 엔진, 새 의존성이 늘면 더 작은 조합을 먼저 비교한다. 한 번 쓰는 코드라도 명확한 책임·보안 경계가 필요하면 분리할 수 있다. 줄 수나 소비자 수만으로 정하지 않는다.

여러 화면이나 독립 앱의 디자인·흐름이 다르면 공통 엔진에 억지로 맞추지 않는다. 같은 데이터를 여러 목록에 등록한다면 목록별 역할과 정본을 확인하고 누락·중복 검사 방법을 계획한다. 다른 프로젝트로의 추출은 요청 범위 안일 때만 한다.

## 환경 변수와 공통설정

모든 설계 결정에 환경 변수·설정 영향의 유무를 남긴다. 변경이 없으면 `설정: 변경 없음`과 확인한 경로를 적고, 항목 자체를 생략하지 않는다. 변경이 있으면 값 없이 다음을 기록한다.

환경 변수 이름이나 캐시 입력을 바꾸면 숨김 파일인 `apps/web/.env.schema`를 경로로 직접 열고 기존 검증 모듈·로더·소비자를 대조한다. 파일 목록 검색에는 숨김 파일도 포함한다. 실제 비밀값이 든 `.env` 파일은 출력하지 않는다. 스키마에 이미 있는 기본값·공개성·필수 여부를 읽지 않고 미정으로 남기거나 새 정책으로 덮어쓰지 않는다. 로컬은 소비 앱의 기존 로더·값 공급 방식, Preview·production은 `prokit-deploy`의 공급 위치를 계획에 적는다.

- 변수 이름과 소비 앱·모듈, 기존 로더·검증 위치. Better-T-Stack의 환경 변수 패키지와 서버 전용 모듈을 먼저 쓰고 별도 래퍼를 만들지 않는다.
- 서버 전용·클라이언트 공개, 필수·선택, 기본값, 누락·잘못된 값의 처리. 새 앱 변수는 `apps/web/.env.schema`와 기존 검증 모듈을 맞춘다. 비밀값을 공개 변수나 Client Component에 옮기지 않는다.
- 로컬·Preview·production의 공급 위치와 담당 절차. 실제 값은 문서·출력·예제·커밋에 넣지 않는다. 배포 환경 변경은 `prokit-deploy`를 따른다.
- 빌드 결과에 영향을 주는 변수와 `.env` 파일의 캐시 입력. 소비 앱 태스크에서 확인한다. `passThroughEnv`는 해시에 들어가지 않으므로 결과 변수를 이것만으로 처리하지 않는다. Turbo가 `.env`를 로드한다고 가정하지 않는다.
- 환경별로 달라지는 값과 코드·토큰·도메인 상수의 구별. 고정 링크·한도·디자인 토큰을 이유 없이 환경 변수로 바꾸거나 모든 설정을 거대 객체에 모으지 않는다. 기존 정본을 가져다 쓴다.

## 기존 스킬의 역할

| 판단 | 읽고 적용할 스킬 |
|---|---|
| 필요한 범위와 새 코드의 이유 | 간결성 사다리와 고른 과설계 방지 스킬의 계획 기준(`process-routing.md` 규칙 6 역할 표), 요구·계획 단계의 방법(기본 칸 또는 고른 두뇌) |
| UI 프리미티브와 토큰 | `prokit-ui` → `shadcn`, impeccable |
| 재사용할 React API·boolean 옵션·합성 경계 | `prokit-web` → `vercel-composition-patterns`의 해당 규칙. 단순 재사용에 Context를 강제하지 않는다 |
| 렌더링·데이터 패칭 영향 | `vercel-react-best-practices`의 해당 규칙 |
| 태스크·공유 패키지·환경 변수 캐시 | `turborepo`가 가리키는 설치판 문서 |
| 구현 전 독립 판단 | `prokit-reviewer(plan)`. 고른 두뇌의 계획 리뷰는 있으면 추가 관점으로 사용 |
| 구현된 변경의 품질 | `prokit-reviewer(code)`와 역할 표의 구현 diff 보완 검토 |

프로젝트의 `.agents/skills/<이름>/SKILL.md`를 읽고 실제 적용한 규칙과 결정을 적는다. 이번 프로젝트에 없거나 현재 요청에서 없다고 확인한 스킬은 사용했다고 적지 않는다. 다른 요청·프로젝트에서 읽은 스킬 목록을 이번 사용 증거로 가져오지 않는다. 대체 판단에 참고한 지침과 실제 사용할 수 있는 스킬을 구별한다. 설치 없이 기존 코드·번들 문서로 같은 판단을 수행하고 대체 절차와 한계를 기록한다. 코드 diff용 보완 검토를 계획 문서에 억지로 적용하지 않고 간결성 사다리로 작성한 결정을 독립 리뷰어가 검토한다.

## 구현과 리뷰에 넘기기

계획에는 재사용 경로, 새 코드의 책임, 수정할 파일·소비자, 환경 변수·설정 영향, 만들지 않는 것과 회귀 검사를 연결한다. 위임할 때 결정 위치를 함께 준다. 다른 추출·설정 변경이 필요하면 구현자가 범위 밖 파일을 고치지 않고 코디네이터에게 보고한다.

리뷰어는 계획과 기존 파일을 대조한다. 컴포넌트 복제, 설정 중복, 비밀값 공개, 캐시 입력 누락, 불필요한 추상화를 구체적 소비자·경로와 최소 수정안으로 지적한다. 공통 모듈뿐 아니라 등록 데이터·설정·도구를 바꿀 때도 영향받는 기존 소비자의 경로와 회귀 검사를 적는다. 새 화면 확인으로 기존 화면의 검사를 대신하지 않는다. UI는 빈·오류·키보드 상태를, 환경 변수는 누락과 잘못된 값을 별개 사례로 적고 어느 검증 경계에서 거부되는지 확인한다. 클라이언트 비노출과 캐시 재계산도 검사한다. 관계없는 리팩터링은 백로그로 남긴다.

`audit`은 필수 행의 존재와 증거 형식을 검사한다. 필수 결정 항목과 계획 리뷰의 승인 형식도 확인하지만, 판단의 옳고 그름이나 스킬의 실제 적용을 자동 채점하지 않는다. 독립 계획 리뷰와 동작 평가로 확인한다.
