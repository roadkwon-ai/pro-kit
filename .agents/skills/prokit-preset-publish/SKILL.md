# 프로킷 프리셋 반영

프로킷 웹 반영의 범위·배정·증거·재지시·최종 검수를 관리한다. 제품 제작과 문서·배포의 기술 지침을 이 스킬에 다시 쓰지 않는다.

## 시작과 경계

1. 요청을 공식 프리셋 제작, 완성품의 로컬 등록, 기존 카탈로그 편집·보관·복구, 외부 게시 중 필요한 범위로 정한다. 일반 사용자 앱 제작이면 제품 프로젝트의 스킬로 넘기고 카탈로그·운영 미리보기를 추가하지 않는다.
2. 사용자가 지정한 pro-kit, pro-kit-web, pro-kit-samples와 제품·팩·정적 출력 경로를 확인한다. 기존 변경·HEAD·관련 파일 해시·통과 증거와 현재 배포 보류를 고정한다. 홈을 추측해 찾지 않는다.
3. [publication.md](references/publication.md)에서 이번 반영의 정본·소비자·검사를 확인한다. 아래 명령으로 현재 등록 상태와 시스템 기준선을 대조한다. 달라졌으면 `prokit-preset-maintain`으로 변경된 계약부터 검토한다. 필요한 제공자나 검증 도구가 없으면 `blocked`로 남기고 임의 대체 구현을 하지 않는다.

```bash
node <prokit-preset-maintain>/scripts/check-contract.mjs --web <pro-kit-web> --kit <pro-kit> --slug <이름>
```

미등록 새 프리셋은 누락 위치를 반영 계획에 적는다. 먼저 공통 시스템이 변했는지 확인하고, 등록 후 같은 계약 검사를 다시 한다. 미등록을 이유로 전체 시스템 기준선을 무조건 새것으로 바꾸지 않는다.

## 카탈로그 관리

등록·카테고리 이동·태그·제목·설명 수정·보관·복구는 [publication.md](references/publication.md)의 카탈로그 절차를 따른다. 기존 공통 카드·상세·미리보기를 재사용하고, 파일 저장과 외부 게시를 구분한다. DB나 관리 화면이 이미 있다고 가정하지 않는다.

## 제작과 반영

- 제작이 필요하면 `prokit-preset-create`로 연결한다. 원본 관측과 COPY 검수는 preset 제작 스킬이 소유한다. `prokit-preset-verify`의 독립 충실도 결과, 완성팩 복원 증거, `prokit-docs`의 문서 결과를 회수한 뒤 등록한다. 기능 QA만 통과한 결과를 완성품으로 게시하지 않는다.
- 프로킷 부모 설정과 공식 프리셋을 연결할 때만 [preview-settings.md](references/preview-settings.md)를 읽는다. 공통 팔레트·서체·수신기·내보내기를 재사용하며 일반 서비스에는 운영 미리보기 수신기를 넣지 않는다.
- 웹 부품과 설정 통합은 한 수행자가 맡는다. 파일·출력 소유권이 분리된 제품·문서 작업만 병렬 배정한다. 전체 타입·린트·빌드는 통합 담당자가 선택한다. 변경된 파일을 쓰는 곳을 확인하고 내장 전문 리뷰와 중복되는 리뷰를 추가하지 않는다.
- 문서 구조와 공통 값은 접근 가능한 `prokit-docs`, 한국어 검수는 `prokit-writing`에 맡긴다. 없으면 해당 원본·프로젝트 정본을 확인하는 전문 수행자에게 배정하고 사용 출처를 남긴다. 일반 기술 문서를 복제하거나 설치 manifest를 일회성 사용의 허용 목록으로 취급하지 않는다.
- [measurements.md](references/measurements.md)대로 실제 실행 기록을 보존한다. 필요한 단계에 [record-command.mjs](scripts/record-command.mjs)를 사용할 수 있다. 관측 일부·전체 제작·재현 예상과 토큰·비용의 측정 상태를 구분한다.
- 자원 guard의 `unknown`·`block`이면 새 설치·생성·빌드·내보내기·QA를 시작하지 않는다. 읽기·진단은 계속할 수 있다. 환경·캐시 크기만으로 삭제하지 않는다.

guard는 제품의 `scripts/resource-guard.mjs`를 우선 사용하고 없으면 pro-kit 템플릿의 기존 helper를 사용한다. 해당 작업공간에서 `node <guard> check`의 `status`·`reasons`·`measurement`를 회수하며, 인식된 root·오류·시간 예산을 진단한다. 범위 밖을 탐색하거나 차단을 없애려고 정책 값을 올리지 않는다.

## 수용과 게시

등록 계약 검사와 실제 제품·설정 검사를 구분한다. 새 사이트는 전체 범위, 수정은 실패·변경 기능·공유 소비자를 확인한다. 개발 서버와 정적 결과물의 증거를 각각 확보한다. 입력·환경·도구·대상이 같은 통과 증거만 재사용하고 `unknown`·누락·미해결 flaky를 PASS로 만들지 않는다.

전문 리뷰 충족 범위는 재사용하되 독립 최종 `prokit-reviewer` 또는 프로젝트의 검증된 최종 리뷰 게이트는 매번 수행한다. 수정은 원 수행자에게 묶어 최대 두 차례 재지시하고 영향 검사만 수행한다. JSON 결과·해시·관리 스크립트의 성공은 발행 권한이나 Main 콜백의 인수 증명이 아니다.

로컬 준비 요청이나 배포 보류가 있으면 `published:false`를 유지한다. 외부 게시가 현재 허가된 경우에만 기존 팩·릴리스·Pages·Vercel 절차로 수행하고 실제 원격 결과를 확인한다. `.envrc`·`.env` 등 사용자가 지정한 인증 정본의 키 존재·적용 순서를 값 없이 확인한 뒤에만 새 로그인을 요청한다. 사용자 `[confirm]`을 대신 채우지 않는다.

보고에는 변경 파일, 사용한 스킬·출처, 실제 명령·종료 코드, 관측 시간·자원 판정, 재사용·실행한 검사, 리뷰 범위·미해결 사항, 로컬·공개 상태를 구분해 남긴다. 재발 가능한 원인은 기존 lessons와 정본·영향 평가에 좁게 반영한다.
