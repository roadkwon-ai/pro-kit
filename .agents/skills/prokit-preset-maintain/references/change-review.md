# 변경의 영향과 기준선

현재 `preset-contract.mjs`가 낸 `contractFiles`의 경로·내용 해시와 이 스킬의 기준선을 대조한다. 하드코딩한 스킬 설명의 날짜로 최신이라고 판단하지 않는다. 현재 저장소 정본을 먼저 읽고 필요한 참조만 연다.

## 검사 선택

| 바뀐 계약 | 실제 소비자와 필요한 검사 |
|---|---|
| 카탈로그 레코드·편집 CLI | samples.json의 presentation·groups·tagGroups·clones, validatePresetCatalog·changePresetCatalog, 기본 dry-run·부분 병합·불법 입력·원자 저장·보관/복구 fixture, 공통 export·필터·상세·교재 소비자 |
| 카드·상세·측정값 | 공통 값 공급자, home-cards, 상세·툴팁, 실제 브라우저와 unknown/일부 기록 fixture |
| 서체·팔레트·프로필·수신기 | 부모 설정 부품, 적용 옵션·응답, 실제 iframe 서체·의미 토큰과 stale 요청·origin 실패 |
| 내보내기·게시 glue | 원본 명령·guard·제외 범위·공유 출력, 작은 실패 fixture와 변경된 정적 결과 |
| 등록·팩 메타 | 일반 프리셋/클론의 경로, 공개 상태·실제 zip SHA/bytes·문서/이미지 연결 |
| 사용자 템플릿 지침 | 제품 제작 계약과 관리 계약의 경계, 두 템플릿 공통 파일, 관련 형식·행동 검사 |
| 문서·관리 스킬 | 정본과 설치본, 새 쪽의 메뉴·md 주소, 영향받은 행동·참조 검사 |

공유 소비자 확인 없이 실패 목록만 검사하지 않는다. 최신 필수 항목을 먼저 대조해 결함을 수정하고 무거운 검사로 넘어간다. 빌드·내보내기는 동일 공유 출력을 쓰면 직렬로 수행한다. 자원 block·unknown은 추가 대용량 작업의 성공으로 처리하지 않는다.

카탈로그의 보관과 공개 상태를 별도로 확인한다. 보관은 원본·팩·자산을 보존하며, 운영 공개 여부나 원격 파일을 바꾸지 않는다. 향후 DB 전환에서는 같은 레코드 검증·변경 함수를 쓰되 인증·트랜잭션·동시 수정 충돌·캐시 갱신은 실제 DB 도입 범위에서 검증한다. 현재 JSON 검사 통과를 DB 지원 완료로 표현하지 않는다.

## 기준선과 설치

1. 현재 CLI 출력과 변경 파일을 고정하고 이전 검증·원시 실패를 보존한다.
2. 변경 내용과 실제 소비자를 검토하고 필요한 시스템·스킬을 좁게 보완한다. 위임 준비 비용보다 작은 읽기·비교 작업은 직접 수행한다.
3. 새/실패/영향 검사와 독립 리뷰를 회수한다. 형식 검사는 행동·실제 적용의 증거를 대신하지 않는다.
4. 실제 시스템이 고정된 뒤 기준선의 `contractFiles`, `contractFingerprint`, 검수 출처를 갱신한다. 자동으로 현재값을 수용하는 옵션은 두지 않는다.
5. pro-kit과 pro-kit-web의 프로젝트 설치본을 갱신하고 SKILL·참조·스크립트·baseline의 바이트를 정본과 대조한다. 설치가 다른 설정·lock 파일을 바꿨으면 범위를 검토한다.

기본적으로 로컬 관리 점검과 설치만 다룬다. 원격 Git pull·저장소 공개·릴리스·배포·예약 실행은 현재 사용자 요청이 허용한 경우에만 기존 전문 절차를 따른다. 사용자 보류·기존 변경·정본 출처가 불명확하면 임의로 덮어쓰지 않는다.

전문 리뷰는 같은 산출물·스킬 출처·계약·환경·리뷰어인 범위만 재사용한다. 현재 최종 검수와 사용자 `[confirm]`은 대신하지 않는다. 내용 해시는 출처 일치성 자료일 뿐 신뢰·권한을 새로 부여하지 않는다.
