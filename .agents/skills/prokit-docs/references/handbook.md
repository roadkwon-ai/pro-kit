# handbook 쪽

pro-kit `handbook/`은 프로킷이 어떻게 동작하는지 설명하는 문서의 원본이다. 홈페이지 `/docs`가 이것을 복사해 그린다. 따라 하며 만들기는 `tutorials/`가 맡고, 개발 기록(ADR, 설계, 측정 보고서)은 `docs/`에 둔다.

## 순서의 정본

- 묶음 순서: 문서 홈 `handbook/README.md`의 "문서 둘러보기" 표. 첫 칸이 `[묶음 이름](<묶음>/README.md)`, 둘째 칸이 묶음 내용이다.
- 쪽 순서: 묶음 `README.md`의 쪽 표. 첫 칸이 `[쪽 제목](<쪽>.md)`, 둘째 칸이 한 줄 내용이다.
- 표에 없는 `.md`가 있거나 표의 링크가 가리키는 파일이 없으면 `scripts/handbook.test.mjs`가 실패한다. 새 쪽은 파일과 표의 행을 함께 더한다.

## 쪽의 틀

```markdown
# 쪽 제목

> 한눈에: 쉬운 말 2~3문장. 무엇이고 왜 필요한지. **핵심 한 문장은 굵게.**

## 개념이나 흐름을 담은 절

도식, 표, 짧은 설명.

## 자세히

파일, 명령, 규칙. 코드 식별자와 명령은 그대로 쓴다.

## 관련 문서

- [다른 쪽 제목](다른-쪽.md)
```

- 첫 세 줄은 `# 제목`, 빈 줄, `> 한눈에: `로 시작한다(테스트가 본다). 한눈에 문단은 전문 용어 없이 처음 보는 사람이 읽고 멈춰도 되게 쓴다.
- 앞부분 절 이름은 내용을 말한다. 이웃 쪽의 절 구성을 따른다.
- 거의 모든 쪽이 `## 관련 문서` 바로 앞에 `## 자세히` 절을 둔다. 파일, 명령, 규칙은 그 절에 모은다.
- 마지막 절은 `## 관련 문서`다. 같은 묶음과 다른 묶음의 쪽, 튜토리얼 가이드를 링크한다.
- 문체는 해요체다. 표 칸이 문장이면 해요체로 끝낸다.

묶음 소개(`<묶음>/README.md`)는 `# 묶음 이름`, 빈 줄, `> 한눈에: ` 문단, `| 쪽 | 내용 |` 표 순서다. 문서 홈은 핵심 표와 "문서 둘러보기" 표를 둔다.

## 중복 규칙

- 비용과 키, Windows, 문제 해결, 용어 풀이는 `tutorials/reference/`의 가이드(`costs-and-keys.md`, `windows.md`, `troubleshooting.md`, `glossary.md`)로 링크하고 다시 쓰지 않는다.
- 외부 서비스(Vercel, Neon, Supabase 등)의 요금표와 한도 수치를 handbook에 옮기지 않는다. 바뀌면 문서가 틀리고 검사도 잡지 못한다. 공식 페이지 링크와 프로킷이 기대는 조건(예: Hobby 요금제의 되돌리기 제한)만 쓴다. 프로킷이 기대는 판과 날짜는 이미 있는 값 키(`vercel.node`, `vercel.node20Stop`, `node.eol`, `supabaseCli.min` 등)로 쓰고, 새로 필요하면 출처와 날짜를 보고에 적는다. 사용자가 요금이나 한도를 다루는 쪽을 직접 청했으면 멈춰서 묻지 말고 이 규칙 안에서 쪽을 만든 뒤, 옮기지 않은 수치와 이유를 보고에 적는다. 요금·한도 쪽에서는 조건을 숫자 없이 쓴다. 그 쪽의 숫자는 이미 있는 값 키만 쓰고, 새 값 키나 맨숫자는 만들지 않는다. 필요해 보이는 수치는 출처와 함께 보고에만 적는다.
- 다른 쪽에 있는 설명은 다시 쓰지 않고 링크한다. 같은 글이 두 문서 이상에 남으면 `scripts/doc-values.test.mjs`의 중복 검사가 실패한다. 문턱값과 검사 범위는 pro-kit `docs/common-values.md` "규칙" 절이 정본이다.
- 템플릿의 명령, 스킬, 구성을 바꾸면 관련 쪽(비교표 `templates/choose.md`, 도식, 폴더 구조 `reference/project-structure.md`)도 맞춘다.

## 사실 대조

쪽마다 재료와 대조한다. 재료는 템플릿 파일(`templates/<템플릿>/files/`), 템플릿 README, 스킬 `SKILL.md`, `VERIFICATION.md`, `AGENTS.md`다. 템플릿 파일에서 확인되지 않는 내용은 쓰지 않는다. 두 템플릿 중 한쪽에만 있는 내용을 두 템플릿 모두의 것처럼 쓰지 않는다. 확인하지 못한 것은 보고한다.

## 링크와 앵커

- 링크는 상대 경로로 쓴다. handbook 밖의 pro-kit 파일도 링크할 수 있다(홈페이지가 GitHub 주소로 바꾼다). 저장소 밖을 가리키는 상대 링크는 쓰지 않는다.
- 앵커는 GitHub 규칙을 따른다. 제목을 소문자로 바꾸고 글자, 숫자, 공백, 하이픈, 밑줄만 남긴 뒤 공백을 하이픈으로 바꾼다. 같은 쪽에서 되풀이되는 제목에는 `-1`, `-2`를 붙인다. 제목에 값 표시가 있으면 주석을 지운 글로 계산한다.
- 제목을 바꾸면 그 앵커를 쓰는 링크를 저장소 전체에서 찾아 고친다.

## 도식과 그림

- 도식은 ` ```mermaid ` 코드 블록이다. GitHub와 홈페이지 모두 그린다. 홈페이지는 도식마다 내려받기를 붙인다.
- 코드 블록 안에는 값 표시를 달 수 없다. 도식에 값이 들어가면 블록 전체를 글 묶음으로 만든다([shared-values.md](shared-values.md)).
- 그림은 `.webp`로 두고, 무엇을 보여 주는지 대체 글을 쓴다.

## 쪽 옮기기·지우기

1. 옛 묶음 쪽 표에서 행을 빼고 새 묶음 쪽 표에 더한다. 묶음을 새로 만들거나 없애면 문서 홈 표도 고친다.
2. 저장소 전체에서 옛 파일 이름과 앵커를 가리키는 링크를 찾아 고친다(`git grep`으로 handbook, tutorials, README, CONTRIBUTING, 템플릿 README에서 파일 이름을 찾는다). 튜토리얼 장을 옮기거나 번호를 바꾸면 과정 첫 쪽의 장 표, 이웃 장 끝의 `다음:` 링크, 묶음 표시 인자 안의 파일 이름(예: `auth=05-auth-profiles.md`)도 고친다.
3. 옛 경로를 적은 `scripts/doc-values.cases.mjs`의 CASES, `docs/dupes-allow.txt`, `docs/time-allow.txt` 항목을 새 경로로 바꾼다.
4. 쪽에 글 묶음이 있으면 묶음 원본의 상대 링크가 새 깊이에서도 맞는지 본다. 묶음은 같은 깊이의 쪽에서만 쓴다.
5. 홈페이지 주소와 `.md` 주소가 바뀐다. 바뀐 주소를 보고한다([page-actions.md](page-actions.md)).

## 홈페이지 반영

pro-kit-web에서 sync와 검사를 돌린다(명령은 `SKILL.md`의 검사 명령 표). 새 묶음이나 새 쪽을 더하면 문서 메뉴와 `.md` 주소가 붙는지도 확인한다([page-actions.md](page-actions.md)).
