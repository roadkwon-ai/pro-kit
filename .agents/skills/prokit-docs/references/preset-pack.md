# 프리셋 팩 문서와 인계

팩 문서는 완성 프리셋을 복원하고 개인화한 뒤 실전 개발로 이어 가는 안내다. 팩의 위치·파일 이름·명령은 담당 저장소의 실제 계약을 먼저 확인한다. 아래 파일을 기계적으로 만들지 않고 해당 팩이 제공하는 문서만 작성한다.

## 책임과 입력

`pro-kit-preset-skills`는 원본 조사·COPY·자산 생성·촬영·품질 판정·팩 조립을 맡는다. `pro-kit`은 완성팩 적용·화면 개발·실전 기능 연결을 맡는다. `prokit-docs`는 그 결과를 설명하는 문서와 교재, 인계 자료의 구조·사실 검수를 맡는다.

문서 작성 전에 기술 담당에게서 다음 자료를 받거나 확인 가능한 정본에서 읽는다.

- 문서가 설명할 제품 버전과 실행 소스·자산 fingerprint, 팩 manifest와 소스 무결성 목록의 위치
- 실제 실행한 검증 명령, 조건, 결과와 로그 위치
- 실제 지원 페이지·테마·언어·모션·상호작용, 데모와 실연동의 구분
- 바꿀 수 있는 설정·콘텐츠·자산과 유지할 구조, 충돌 처리와 복원 절차
- 자산 출처·라이선스, 생성 자산 여부와 교체 조건
- 승인된 캡처와 재현 조건, 미검증 항목, 로컬·미게시 여부

기술 사실이 충돌하면 해당 주장만 보류하고 충돌한 정본·증거를 기술 담당에게 돌려보낸다. 확인된 부분은 계속 작성한다. 자료가 부족하다고 원본 사이트 재조사나 새 디자인 선택을 사용자에게 권하지 않는다. 팩 활용의 비교 기준은 완성 프리셋이다.

## 문서별 내용

| 문서 | 담을 내용 |
|---|---|
| `README.md` | 팩의 목적·실제 포함 내용·지원 환경·복원 순서·첫 실행·데모 한계 |
| `CUSTOMIZE.md` | 실제 수정 지점·허용 범위·보존할 구조·변경 후 비교 방법 |
| `screens.md` | 실제 페이지와 경로·주요 상태·승인 캡처·기능과 데모 설명 |
| `SOURCES.md` | 확인된 자산 출처·라이선스·생성 여부·교체 조건 |
| 교재·활용 안내 | 팩 복원 → 개인화 → 실제 기능 연결 → 회귀 확인 순서와 검증한 명령 |
| 제작·활용 인계 안내 | 각 담당의 입력·출력·실제 증거와 남은 확인 사항 |

캡처는 승인된 자료 중 목적에 맞는 것을 선택·배치하고 설명한다. 촬영·원본 대비 품질 합격 판정, 실행 소스·자산·JSON 계약·생성 프롬프트 제작은 기술 담당에게 맡긴다. 생성 프롬프트 파일의 위치를 설명할 수 있으나 내용을 대신 설계하지 않는다.

문서는 해요체로 쓴다. 스킬·규칙과 기술 인계 기록은 `prokit-writing` 문체 표를 따른다. 기술 스킬의 판단 규칙을 문서 관례로 덮어쓰지 않는다.

## 가상 정보와 개인화 안내

레퍼런스를 가상 정보로 바꾼 팩은 값뿐 아니라 항목의 역할과 구성을 보존했는지 기술 담당의 대응표로 확인한다. 푸터의 상호·대표자·등록번호·주소·연락처·저작권·소셜과 정책 링크처럼 본문 밖에 있는 항목도 개인화 안내에서 빠뜨리지 않는다. 문서 작성자가 누락된 항목을 임의로 설계하거나 원본의 실제 사업자 정보를 예시에 복사하지 않는다. 확인된 참고 출처 URL은 조사·출처 기록으로 보존하며 운영 계정·판매·영상 연결용 URL의 가상화와 구분한다.

`CUSTOMIZE.md`에는 실행 소스에서 확인한 설정 위치, 언어 간 공유 여부, 빈 링크의 동작, 실제 사용 전 교체할 예시 값을 적는다. 사업자 데이터가 공통 설정을 읽더라도 페이지별 라벨·구분자·줄 구성까지 같다고 쓰지 않는다. 실제 화면별 구성을 인계 자료에 보존한다. 설정 값 보존이 필요한 안내는 전체 설정 블록을 다시 쓰기보다 경로·수정 키를 연결하고, 전체 코드 인용이 필요하면 원문 그대로 복사해 값별로 대조한다. 가상 등록번호·실적은 실제 등록·성과처럼 설명하지 않고, 샘플 주소를 실제 연락 가능한 주소로 소개하지 않는다. 예시 코드에서 새로운 실재 가능 인물·도메인·주소를 만들지 않으며, 실제 운영 값은 사용자가 확인한 정보로 직접 교체하도록 안내한다. URL이 비어 있다는 이유로 원본 구성의 항목 제거를 권하지 않는다. 레퍼런스의 항목을 생략하거나 동작을 바꾼 경우에는 확인된 차이와 이유를 남기고 기술 담당에게 보완을 요청한다.

## 작성과 검사 순서

1. 제품 검수 결과와 fingerprint를 확인하고 문서를 작성한다. 미게시 로컬 팩은 로컬 경로와 실제 준비 상태로 안내한다. 없는 다운로드·배포 주소를 만들지 않는다.
2. 명령·옵션·파일 경로·지원 기능을 실행 소스와 인계 자료에 대조한다. 기술 담당에게 사실 확인을 맡긴다. 문서 때문에 실행 소스가 바뀌면 제품 검증을 다시 수행하도록 돌려보낸다.
3. 팩 담당이 문서를 포함한 최종 ZIP을 조립한다. 복원 환경에서 문서의 명령을 재현하고 페이지·링크·상태를 확인한다. 실행하지 못한 명령은 미검증으로 기록한다.
4. 팩 담당이 최종 ZIP 해시를 외부 인덱스에 기록한다. 자기 ZIP의 SHA를 ZIP 안 문서에 넣고 다시 압축하는 순환을 만들지 않는다. 제품 fingerprint와 최종 ZIP 해시를 혼동하지 않는다.
5. 홈페이지에 나오는 교재는 문서 정본에서 동기화하고 `SKILL.md`의 홈페이지 검사 명령을 수행한다. 팩 내부 문서에 홈페이지 쪽 메뉴나 공통 값 표시를 강제로 넣지 않는다.

측정하지 않은 시간·비용·점수, 실행하지 않은 복원·빌드·시각 검증을 완료로 쓰지 않는다. 파일의 존재나 형식 검사 통과는 실제 복원과 화면 품질의 증거가 아니다. 알려진 미검증 한계는 문서와 보고에 같은 의미로 남긴다.

## 인계 결과

바뀐 문서, 연결한 제품 fingerprint, 대조한 증거, 실제 실행 결과와 미검증 항목을 기술 담당에게 전달한다. 문서 완료가 제품 품질 승인·게시 권한을 대신하지 않는다.
